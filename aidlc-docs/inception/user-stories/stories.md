# 1. EPIC: 작품 관리 (Title Management)

관련 요구사항: FR-001, FR-002, FR-003

## US-001 — 작품 등록
**Scout**로서, 발굴한 작품을 시스템에 등록하고 싶다. 왜냐하면 흩어진 스프레드시트 대신 한 곳에서 후보를 관리해야 중복 검토와 누락을 막을 수 있기 때문이다.

**관련**: FR-001 · **페르소나**: Scout

```gherkin
Given Scout로 로그인한 상태이고
When 제목, 원제, 감독, 출연, 장르, 러닝타임, 제작국가, 제작언어, 제작연도, 등급, 시놉시스, 담당자를 입력하고 저장하면
Then 작품이 `발굴(Discovery)` 단계로 생성되고 작품 상세 화면으로 이동한다

Given 작품 등록 화면에서
When 제목 또는 제작연도를 비워두고 저장을 시도하면
Then 저장이 거부되고 해당 필드에 필수 입력 안내가 표시된다

Given 원제 "Anatomie d'une chute", 제작연도 2023인 작품이 이미 존재할 때
When 동일한 원제와 제작연도로 새 작품을 등록하려 하면
Then 중복 가능성 경고가 표시되고, 기존 작품으로 이동하거나 그대로 등록을 진행할 수 있다
```

## US-002 — 작품 정보 수정 및 삭제
**Scout**로서, 등록한 작품의 정보를 고치거나 지우고 싶다. 왜냐하면 초기 정보가 불완전한 채로 등록되는 경우가 많고 잘못 등록한 건은 정리해야 하기 때문이다.

**관련**: FR-001 · **페르소나**: Scout (Analyst·Executive는 조회만) · `[권한 분기]`

```gherkin
Given Scout로 로그인해 작품 상세를 보고 있을 때
When 메타데이터를 수정하고 저장하면
Then 변경 내용이 반영되고 목록·칸반의 표시도 함께 갱신된다

Given Analyst 또는 Executive로 로그인해 작품 상세를 보고 있을 때
When 화면을 확인하면
Then 수정·삭제 버튼이 존재하지 않고, 수정 API를 직접 호출하면 403이 반환된다

Given 평가·코멘트·딜 정보가 딸린 작품이 있을 때
When Scout가 그 작품을 삭제하면
Then 확인 절차를 거친 뒤 작품과 하위 데이터(평가, 코멘트, 딜, 판권, 재무, 단계 이력)가 함께 삭제된다
```

## US-003 — 영화제·수상 이력 기록
**Scout**로서, 작품의 영화제 출품·수상 이력을 남기고 싶다. 왜냐하면 인수 설득의 핵심 근거이자 작품의 시장 가치를 가늠하는 지표이기 때문이다.

**관련**: FR-002 · **페르소나**: Scout

```gherkin
Given Scout로 작품 상세를 보고 있을 때
When 영화제명, 연도, 부문(경쟁/비경쟁), 초청·수상 구분, 수상명, 평단 반응 메모를 입력해 추가하면
Then 이력이 작품에 저장된다

Given 한 작품에 여러 영화제 이력이 등록되어 있을 때
When 작품 상세를 열면
Then 이력이 연도 내림차순으로 정렬되어 표시된다

Given 영화제 이력이 하나도 없는 작품에서
When 작품 상세를 열면
Then 이력 영역이 비어 있는 상태로 정상 표시되고 오류가 발생하지 않는다
```

## US-004 — 작품 검색 및 필터
**모든 역할**로서, 조건을 걸어 작품을 찾고 싶다. 왜냐하면 수백 건의 목록에서 지금 필요한 작품군만 추려봐야 하기 때문이다.

**관련**: FR-003 · **페르소나**: Scout, Analyst, Executive

```gherkin
Given 작품 목록 화면에서
When 제목 일부를 검색어로 입력하면
Then 제목 또는 원제에 해당 문자열을 포함한 작품만 표시된다

Given 작품 목록 화면에서
When 파이프라인 단계, 장르, 제작국가, 제작연도 범위, 담당자 필터를 조합해 적용하면
Then 모든 조건을 동시에 만족하는 작품만 표시된다

Given 필터가 적용된 목록을 보고 있을 때
When 페이지를 새로고침하거나 해당 URL을 다른 사용자에게 전달하면
Then 동일한 필터 조건이 그대로 복원된다
```

# 2. EPIC: 인수 파이프라인 (Acquisition Pipeline)

관련 요구사항: FR-004, FR-005, FR-006, FR-007

## US-005 — 칸반 보드로 파이프라인 조회
**모든 역할**로서, 작품이 어느 단계에 몇 편 있는지 보드로 보고 싶다. 왜냐하면 목록만으로는 파이프라인 전체의 흐름과 정체를 파악할 수 없기 때문이다.

**관련**: FR-004, FR-007 · **페르소나**: Scout, Analyst, Executive

```gherkin
Given 시스템에 작품이 등록되어 있을 때
When 칸반 보드를 열면
Then 발굴 / 스크리닝 / 평가 / 오퍼 / 협상 / 계약체결 / 반려 7개 열이 순서대로 표시되고 각 열에 해당 단계의 작품 카드와 건수가 나타난다

Given 칸반 보드를 보고 있을 때
When 작품 카드를 확인하면
Then 제목, 담당자, 종합 평가 점수, 마지막 단계 변경일이 카드에 표시된다

Given 어떤 단계에 작품이 한 건도 없을 때
When 보드를 확인하면
Then 해당 열이 빈 상태로 유지되며 열 자체는 사라지지 않는다
```

## US-006 — 드래그로 단계 변경
**Scout·Analyst**로서, 작품 카드를 끌어 다른 단계로 옮기고 싶다. 왜냐하면 진행 상황이 바뀔 때마다 별도 화면에 들어가지 않고 즉시 반영하고 싶기 때문이다.

**관련**: FR-005, FR-007 · **페르소나**: Scout, Analyst · `[권한 분기]`

```gherkin
Given Scout 또는 Analyst로 칸반 보드를 보고 있을 때
When 작품 카드를 다른 단계 열로 끌어놓으면
Then 승인 절차 없이 즉시 단계가 변경되고 보드의 건수와 금액 합계가 갱신된다

Given 단계를 변경할 때
When 사유 메모를 입력하거나 비워둔 채 확정하면
Then 어느 쪽이든 변경이 완료되고 이력에 기록된다

Given 작품이 `계약체결` 또는 `반려` 상태일 때
When 이전 단계로 카드를 끌어 옮기면
Then 오기입 정정 목적의 되돌리기로 허용되고 이력에 기록된다
```

## US-007 — 열람 전용 역할의 단계 변경 차단
**Executive**로서, 내가 실수로 데이터를 바꾸지 못하게 하고 싶다. 왜냐하면 나는 현황을 확인하는 사람이지 실무 데이터를 수정하는 사람이 아니기 때문이다.

**관련**: FR-005, FR-007, FR-022 · **페르소나**: Executive · `[권한 분기]`

```gherkin
Given Executive로 로그인해 칸반 보드를 보고 있을 때
When 작품 카드를 끌려고 시도하면
Then 카드가 움직이지 않고 드래그가 비활성화되어 있다

Given Executive 세션의 인증 정보로
When 단계 변경 API를 직접 호출하면
Then 403이 반환되고 단계와 이력에 아무 변화가 없다
```

## US-008 — 단계 변경 이력과 체류 기간 조회
**모든 역할**로서, 작품이 어떤 경로로 지금 단계에 왔고 각 단계에 얼마나 머물렀는지 보고 싶다. 왜냐하면 어디서 지연이 발생하는지 알아야 병목을 개선할 수 있기 때문이다.

**관련**: FR-006 · **페르소나**: Scout, Analyst, Executive · `[PBT]`

```gherkin
Given 여러 번 단계가 변경된 작품이 있을 때
When 작품 상세의 이력 영역을 열면
Then 이전 단계, 이후 단계, 변경자, 변경 시각, 사유 메모가 시간순으로 표시된다

Given 이력 목록을 보고 있을 때
When 각 항목을 확인하면
Then 해당 단계에 머문 기간이 일수로 함께 표시되고, 현재 단계는 오늘까지 경과한 일수가 표시된다

Given 임의의 단계 변경 이력이 주어졌을 때 `[PBT]`
When 체류 일수를 계산하면
Then 모든 체류 일수는 0 이상이고, 체류 일수의 총합은 최초 등록 시각부터 현재까지의 경과 일수와 일치한다

Given 단계 변경 이력이 저장되어 있을 때
When 이력을 수정하거나 삭제하려 시도하면
Then 수정·삭제 수단이 제공되지 않으며 API 호출도 거부된다
```

# 3. EPIC: 평가 및 협업 (Evaluation & Collaboration)

관련 요구사항: FR-008, FR-009, FR-010

## US-009 — 평가 스코어카드 작성
**Scout**로서, 본 작품의 평가를 구조화된 형태로 남기고 싶다. 왜냐하면 "좋았다"는 메모만으로는 나중에 판단 근거를 재구성할 수 없기 때문이다.

**관련**: FR-008 · **페르소나**: Scout · `[권한 분기]`

```gherkin
Given Scout로 작품 상세를 보고 있을 때
When 작품성·상업성·화제성·타깃 적합성을 각 1~5점으로 매기고 총평, 시사 기록(시사일·장소·참석자), 타깃 관객층을 입력해 저장하면
Then 평가가 작성자·작성시각과 함께 저장된다

Given 이미 다른 Scout의 평가가 있는 작품에서
When 두 번째 Scout가 평가를 추가하면
Then 기존 평가를 덮어쓰지 않고 평가자별로 나란히 보존된다

Given 점수 범위를 벗어난 값(0 또는 6)을 입력했을 때
When 저장을 시도하면
Then 저장이 거부되고 허용 범위 안내가 표시된다

Given Analyst 또는 Executive로 작품 상세를 볼 때
When 평가 영역을 확인하면
Then 평가 내용은 읽을 수 있으나 작성·수정 수단은 제공되지 않는다
```

## US-010 — 종합 점수 자동 산출
**모든 역할**로서, 작품 목록에서 평가 점수를 한눈에 비교하고 싶다. 왜냐하면 상세로 들어가지 않고도 후보 간 상대적 위치를 알아야 하기 때문이다.

**관련**: FR-008 · **페르소나**: Scout, Analyst, Executive

```gherkin
Given 작품에 항목별 점수가 입력된 평가가 있을 때
When 작품 목록 또는 칸반 카드를 보면
Then 항목별 점수의 평균이 종합 점수로 표시된다

Given 한 작품에 평가가 여러 건일 때
When 종합 점수를 확인하면
Then 전체 평가의 평균값이 표시되고 평가 건수가 함께 나타난다

Given 평가가 한 건도 없는 작품일 때
When 목록에서 확인하면
Then 종합 점수 자리에 `미평가`가 표시되고 0점으로 계산되지 않는다
```

## US-011 — 작품별 코멘트
**모든 역할**로서, 작품에 의견을 남기고 싶다. 왜냐하면 이메일로 흩어지던 논의가 작품에 붙어 축적되어야 나중에 맥락을 찾을 수 있기 때문이다.

**관련**: FR-009 · **페르소나**: Scout, Analyst, Executive

```gherkin
Given 아무 역할로든 로그인해 작품 상세를 보고 있을 때
When 코멘트를 작성하면
Then 작성자·작성시각과 함께 저장되고 목록 최상단에 표시된다

Given 내가 작성한 코멘트가 있을 때
When 수정 또는 삭제를 시도하면
Then 정상 처리된다

Given 다른 사용자가 작성한 코멘트가 있을 때
When 수정·삭제를 시도하면
Then 수단이 제공되지 않으며 API 호출 시 403이 반환된다
```

## US-012 — 멘션 알림
**모든 역할**로서, 특정 담당자를 코멘트에서 호출하고 싶다. 왜냐하면 확인이 필요한 건을 별도 연락 없이 시스템 안에서 전달해야 하기 때문이다.

**관련**: FR-010, FR-019 · **페르소나**: Scout, Analyst, Executive

```gherkin
Given 코멘트를 작성하고 있을 때
When `@사용자명` 형태로 다른 사용자를 언급해 저장하면
Then 언급된 사용자의 알림 센터에 멘션 알림이 생성된다

Given 멘션 알림을 받은 사용자가
When 알림을 클릭하면
Then 해당 작품 상세의 그 코멘트 위치로 이동한다

Given 코멘트에 세 명이 멘션되었을 때
When 알림 생성 결과를 확인하면
Then 멘션된 세 명에게만 알림이 생기고 작성자 본인에게는 생기지 않는다
```

# 4. EPIC: 딜 · 판권 · 재무 (Deal, Rights & Financials)

관련 요구사항: FR-011, FR-012, FR-013

## US-013 — 딜 정보 기록
**Analyst**로서, 작품의 딜 조건을 기록하고 싶다. 왜냐하면 오퍼 금액과 유효기간이 관리되지 않으면 만료로 기회를 잃기 때문이다.

**관련**: FR-011 · **페르소나**: Analyst · `[권한 분기]`

```gherkin
Given Analyst로 작품 상세의 딜 영역을 보고 있을 때
When 요청가, 오퍼 금액, 오퍼 제출일, 오퍼 유효기간, MG, 러닝 로열티율, 계약 조건 메모를 입력해 저장하면
Then 딜 정보가 작품에 저장된다

Given 금액 필드에 값을 입력할 때
When 저장 후 다시 조회하면
Then 값이 KRW 정수로 보존되고 화면에는 천 단위 구분 기호가 적용되어 표시된다

Given 로그인 상태에서
When 브라우저를 완전히 종료한 뒤 다시 접속하면
Then 세션이 만료되어 로그인 화면이 표시된다
```

## US-027 — 서버 측 권한 강제
**Executive**로서, 권한 제어가 화면 숨김이 아니라 실제로 막혀 있길 원한다. 왜냐하면 UI만 가려진 권한은 권한이 아니기 때문이다.

**관련**: FR-022 · **페르소나**: Scout, Analyst, Executive · `[권한 분기]` **← 핵심 스토리**

```gherkin
Given 권한 매트릭스에 정의된 11개 기능 항목이 있을 때
When 각 역할로 허용되지 않은 기능의 API를 직접 호출하면
Then 모든 경우에 403이 반환되고 데이터가 변경되지 않는다

Given 마스킹 대상 필드가 있는 응답에서
When 권한 없는 역할이 조회하면
Then 해당 필드가 응답 페이로드에서 제거되어 전달된다

Given 브라우저 개발자 도구로 클라이언트 상태를 조작했을 때
When 숨겨진 UI 요소를 강제로 노출시켜 조작하면
Then 서버가 요청을 거부하므로 실제 데이터 변경은 발생하지 않는다
```

## US-028 — 사용자 계정 관리
**Executive**로서, 팀원 계정을 만들고 역할을 지정하고 싶다. 왜냐하면 새 구성원이 합류할 때마다 접근 권한을 부여해야 하기 때문이다.

**관련**: FR-023 · **페르소나**: Executive · `[권한 분기]`

```gherkin
Given Executive로 사용자 관리 화면에 있을 때
When 이메일, 이름, 초기 비밀번호, 역할(Scout / Analyst / Executive)을 지정해 생성하면
Then 계정이 만들어지고 해당 사용자가 로그인할 수 있다

Given 기존 사용자가 있을 때
When 역할을 다른 값으로 변경하면
Then 변경이 즉시 반영되어 다음 요청부터 새 역할의 권한이 적용된다

Given Scout 또는 Analyst로 로그인한 상태에서
When 사용자 관리 화면에 접근하려 하면
Then 접근이 차단되고 API 호출 시 403이 반환된다
```

## US-029 — 마지막 관리자 보호
**Executive**로서, 실수로 관리자가 한 명도 없는 상태를 만들고 싶지 않다. 왜냐하면 그렇게 되면 아무도 계정을 관리할 수 없어 시스템이 잠기기 때문이다.

**관련**: FR-023 · **페르소나**: Executive

```gherkin
Given 시스템에 Executive 역할 사용자가 단 한 명뿐일 때
When 그 사용자의 역할을 Scout 또는 Analyst로 변경하려 하면
Then 변경이 거부되고 최소 1명의 Executive가 필요하다는 안내가 표시된다

Given 시스템에 Executive 역할 사용자가 단 한 명뿐일 때
When 그 계정을 삭제하려 하면
Then 삭제가 거부된다

Given Executive가 두 명 이상일 때
When 그중 한 명의 역할을 변경하거나 삭제하면
Then 정상 처리된다
```

## US-030 — 단일 명령 로컬 실행
**개발자·평가자**로서, 명령 한 번으로 전체 시스템을 띄우고 싶다. 왜냐하면 포트폴리오를 보는 사람이 복잡한 설치 과정에서 이탈하면 아무것도 보여줄 수 없기 때문이다.

**관련**: NFR-002 · **페르소나**: 전 역할 (설치 주체)

```gherkin
Given 저장소를 새로 내려받은 환경에서
When `docker compose up`을 실행하면
Then 애플리케이션과 PostgreSQL이 함께 기동되고 브라우저에서 접속 가능한 상태가 된다

Given 최초 기동일 때
When 기동 과정을 확인하면
Then 데이터베이스 스키마 마이그레이션과 시드 데이터 적재가 자동으로 수행된다

Given 이미 기동한 적 있는 환경에서
When 다시 기동하면
Then 기존 데이터가 유지되고 시드가 중복 적재되지 않는다

Given 비밀 정보(데이터베이스 접속 정보 등)를 확인할 때
When 소스코드를 검색하면
Then 하드코딩된 값이 없고 환경변수로 주입된다
```

## US-031 — 시드 데이터로 즉시 확인 가능한 첫 화면
**평가자**로서, 접속하자마자 의미 있는 화면을 보고 싶다. 왜냐하면 빈 대시보드로는 이 시스템이 무엇을 하는지 알 수 없기 때문이다.

**관련**: FR-024 · **페르소나**: 전 역할

```gherkin
Given 최초 기동이 완료된 직후
When Scout / Analyst / Executive 데모 계정으로 각각 로그인하면
Then 세 계정 모두 정상 로그인되고 역할별로 다른 화면이 표시된다

Given 시드 데이터만 있는 상태에서
When 대시보드를 열면
Then 파이프라인 현황·포트폴리오 구성·마감 임박 세 위젯이 모두 비어 있지 않은 값을 표시한다

Given 시드 데이터를 확인할 때
When 마감 임박 위젯을 보면
Then 7일 이내 만료 예정인 오퍼가 최소 1건 포함되어 알림 기능을 즉시 확인할 수 있다
```

## US-032 — 한국어·원화 표기 일관성
**모든 역할**로서, 금액과 날짜가 익숙한 형식으로 표시되길 원한다. 왜냐하면 표기가 흔들리면 숫자를 잘못 읽게 되기 때문이다.

**관련**: NFR-004 · **페르소나**: Scout, Analyst, Executive

```gherkin
Given 금액이 표시되는 모든 화면에서
When 값을 확인하면
Then KRW 단일 통화로 천 단위 구분 기호와 함께 표시되고 통화 선택 수단은 제공되지 않는다

Given 날짜가 표시되는 모든 화면에서
When 값을 확인하면
Then `YYYY-MM-DD` 형식으로 표시되고 시간대는 Asia/Seoul 기준으로 계산된다

Given 시스템의 모든 화면에서
When UI 텍스트를 확인하면
Then 한국어로 표시되고 언어 전환 수단은 제공되지 않는다
```

# 10. INVEST 검증 결과

32개 스토리 전체를 INVEST 기준으로 점검했다.

| 기준 | 검증 내용 | 결과 |
|---|---|---|
| **Independent** | 스토리 간 강한 선후 의존을 점검. US-030(로컬 실행)·US-031(시드)은 성격상 다른 스토리의 확인 전제가 되나, 구현 자체는 독립적이므로 별도 에픽(실행 기반)으로 분리함 | ✅ |
| **Negotiable** | 모든 스토리가 "무엇을 왜"만 기술하고 구현 방식(프레임워크, 컴포넌트, API 형태)을 규정하지 않음 | ✅ |
| **Valuable** | 각 스토리가 특정 페르소나의 목표 또는 불만점과 직접 연결됨. US-007·US-014·US-027처럼 "차단"이 목적인 스토리도 해당 페르소나의 명시적 가치(평가 독립성, 우발적 변경 방지)에 연결 | ✅ |
| **Estimable** | 모든 스토리가 단일 화면 또는 단일 기능 경계 안에 있어 규모 판단이 가능 | ✅ |
| **Small** | 스토리당 수용 기준 3~5개 수준으로 유지. FR-011(딜)은 등록(US-013)·마스킹(US-014)으로, FR-013(재무)은 계산(US-016)·열람(US-017)으로, FR-023(사용자 관리)은 관리(US-028)·마지막 관리자 보호(US-029)로 분할함 | ✅ |
| **Testable** | 모든 수용 기준이 Given-When-Then으로 작성되어 테스트로 직접 전환 가능. 권한 관련 기준은 UI가 아닌 **API 응답 수준**에서 검증하도록 기술 | ✅ |

**분할 조치 내역**
- FR-005(단계 변경) → US-006(허용 역할) + US-007(차단 역할) — 역할별 동작 차이를 별도 스토리로 노출
- FR-011(딜 정보) → US-013(기록) + US-014(마스킹) — 마스킹은 이 프로젝트의 핵심 리스크이므로 독립 스토리로 승격
- FR-013(재무) → US-016(계산) + US-017(열람 권한)
- FR-018(내보내기) → US-022 단일 스토리로 유지하되 역할별 결과 차이를 수용 기준으로 분기
- FR-023(사용자 관리) → US-028(관리) + US-029(마지막 관리자 보호)

**권한 매트릭스 커버리지 검증** — requirements.md 3.2절의 12개 권한 항목이 모두 최소 1개 스토리의 수용 기준에 반영됨:
