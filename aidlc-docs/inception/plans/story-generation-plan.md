# 섹션 A. 스토리 분해 방식 선택지

스토리를 어떻게 묶고 나눌지에 대한 5가지 접근법입니다. 섹션 B의 Question 1에서 선택해주세요.

### A-1. User Journey-Based (사용자 여정 기반)
사용자가 실제로 거치는 흐름 순서대로 스토리를 배열한다.
예: `작품 발견 → 등록 → 스크리닝 → 평가 입력 → 오퍼 제출 → 계약 체결`

- **장점**: 흐름의 단절이나 빠진 화면을 발견하기 쉽다. 데모 시나리오를 그대로 만들 수 있다.
- **단점**: 여러 여정에 공통으로 쓰이는 기능(검색, 알림, 권한)이 중복되거나 어디에도 속하지 않는다.
- **적합**: 흐름이 하나로 뚜렷한 제품

### A-2. Feature-Based (기능 기반)
시스템 기능 단위로 묶는다. 요구사항 문서의 5.1~5.7절 구조와 1:1 대응된다.

- **장점**: FR과의 추적성이 가장 명확하다. 구현 단위로 바로 이어진다.
- **단점**: "사용자가 왜 이걸 필요로 하는가"가 흐려지기 쉽다. 기능 목록의 재포장이 될 위험.
- **적합**: 요구사항이 이미 기능별로 정리된 경우

### A-3. Persona-Based (페르소나 기반)
Scout / Analyst / Executive 각각의 관점에서 스토리를 묶는다.

- **장점**: **이 프로젝트의 핵심 난점인 역할별 동작 차이가 정면으로 드러난다.** 같은 화면이 역할마다 다르게 보이는 지점이 누락되지 않는다.
- **단점**: 3역할이 공유하는 기능(작품 조회, 코멘트)이 세 번 반복될 수 있다.
- **적합**: 다중 페르소나 시스템 — 본 프로젝트에 해당

### A-4. Domain-Based (도메인 기반)
비즈니스 도메인 단위로 묶는다. 예: `작품(Title)`, `딜(Deal)`, `판권(Rights)`, `평가(Evaluation)`

- **장점**: 도메인 모델과 정렬되어 이후 Units Generation 분해가 자연스럽다.
- **단점**: 대시보드·리포트처럼 여러 도메인을 가로지르는 기능의 소속이 애매하다.
- **적합**: 도메인 경계가 뚜렷하고 팀이 도메인별로 나뉘는 경우

### A-5. Epic-Based (에픽 계층)
상위 에픽 아래 하위 스토리를 두는 2단계 계층으로 구성한다.

- **장점**: 큰 그림과 세부를 함께 볼 수 있고 진행률 집계가 쉽다.
- **단점**: 계층 관리 오버헤드가 있고, 에픽 자체는 구현 단위가 아니다.
- **적합**: 스토리 수가 30개를 넘어가는 규모

### A-6. 하이브리드 (권장안)
**에픽은 기능 영역(A-2) 기준으로 나누고, 각 에픽 안의 스토리는 페르소나(A-3) 관점으로 작성한다.**
예: 에픽 `딜 및 재무` 안에 `Analyst로서 오퍼 금액을 기록한다` / `Scout로서 MG가 보이지 않는 화면을 본다` 두 스토리가 공존.

- **장점**: FR 추적성(A-2)과 역할별 차이 노출(A-3)을 동시에 확보. 대시보드 같은 횡단 기능도 자연스럽게 배치된다.
- **단점**: 두 축을 동시에 관리해야 하므로 작성 규칙을 명확히 해야 한다 (→ Question 2, 3에서 확정)

## Question 2

B) **굵은 단위** — 하나의 스토리 = 하나의 기능 영역. 약 10~15개 스토리. 빠르게 훑기 좋지만 수용 기준이 길어짐

C) **잘게 나눔** — CRUD의 각 동작을 개별 스토리로. 50개 이상. 진행률 추적은 세밀하나 문서 관리 부담이 큼

X) 기타 (아래 [Answer]: 뒤에 설명해주세요)

## Question 3

## Question 4

C) **혼합** — 핵심 흐름은 Given-When-Then, 부수 조건은 체크리스트
