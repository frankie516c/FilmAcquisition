# 섹션 B. 질문 (답변 필요)

## Question 1 — 계층 구조
애플리케이션을 어떤 계층으로 나눌까요?

A) **3계층 + 순수 도메인 모듈** — `API 경계 → 애플리케이션 서비스 → 리포지토리`의 3계층을 두고, 계산·판정 로직은 어느 계층에도 의존하지 않는 **순수 함수 모듈**로 따로 뺀다 (**권장** — PBT 대상 4개를 프레임워크 없이 테스트할 수 있고 NFR-008의 단일 정의 제약을 지키기 쉬움)

B) **간이 헥사고날 (포트-어댑터)** — 도메인을 중심에 두고 DB·HTTP·파일을 어댑터로 분리. 교체 가능성이 높지만 PoC 규모에는 보일러플레이트가 많다

C) **2계층 (얇은 서비스)** — API 핸들러에서 Prisma를 직접 호출하고 공통 로직만 헬퍼로 추출. 가장 빠르지만 재무 계산 중복과 마스킹 누락 위험이 커진다

X) 기타 (아래 [Answer]: 뒤에 설명해주세요)

[Answer]: A

## Question 2 — API 스타일
클라이언트와 서버는 어떤 방식으로 통신할까요?

A) **REST Route Handlers 중심** — `app/api/**/route.ts`에 REST 엔드포인트를 두고 클라이언트에서 호출한다 (**권장** — US-014·US-027의 수용 기준이 *"API를 직접 호출하면 403"*, *"응답 페이로드에 키가 없다"* 로 기술되어 있어, 검증 가능한 HTTP 경계가 명시적으로 존재해야 함)

B) **Server Actions 중심** — 폼 제출과 변경을 Server Action으로 처리. 코드가 간결해지지만 "API를 직접 호출해 403을 확인"하는 테스트가 어려워진다

C) **혼합** — 조회는 서버 컴포넌트에서 직접, 변경은 Server Action, 외부 소비가 필요한 것만 REST

X) 기타 (아래 [Answer]: 뒤에 설명해주세요)

[Answer]: A

## Question 3 — 권한·마스킹 강제 지점 ★ 가장 중요
역할별 필드 제거를 어디서 강제할까요?

A) **필드 정책 테이블 + 단일 직렬화 게이트** — `{엔티티.필드 → 접근 가능 역할}` 정책을 한 곳에 선언하고, 모든 응답이 반드시 통과하는 단일 직렬화 함수가 이 정책에 따라 필드를 제거한다. 화면·CSV·PDF·Excel 네 경로가 같은 게이트를 지난다 (**권장** — 새 필드가 추가돼도 정책 테이블에 한 줄 넣으면 전 경로에 적용되고, 누락 시 기본값을 "차단"으로 두면 실수가 노출로 이어지지 않음)

B) **역할별 DTO 매퍼** — 역할마다 별도의 응답 타입과 매퍼 함수를 정의한다. 타입 수준에서 명확하지만 역할이나 필드가 늘면 매퍼가 조합 폭발한다

C) **서비스별 개별 처리** — 각 서비스가 자기 응답에서 필요한 필드를 제거한다. 구현은 단순하나 누락 시 발견이 어렵다

X) 기타 (아래 [Answer]: 뒤에 설명해주세요)

[Answer]: A

## Question 4 — 데이터 접근
Prisma를 어떻게 다룰까요?

A) **리포지토리로 감싸기** — 서비스는 리포지토리 인터페이스만 알고 Prisma를 직접 모른다. 테스트 시 리포지토리를 대체할 수 있다 (**권장** — 서비스 단위 테스트에 DB가 필요 없어지고, append-only 규칙(FR-006)을 리포지토리에서 강제할 수 있음)

B) **서비스에서 Prisma 직접 사용** — 중간 계층이 없어 코드가 짧다. 대신 서비스 테스트에 실제 DB 또는 테스트 컨테이너가 필요하다

## Question 5 — 컴포넌트 경계 기준
컴포넌트(모듈)를 무엇을 기준으로 나눌까요?

A) **기능 영역(에픽) 기준** — 작품 / 파이프라인 / 평가·협업 / 딜·재무 / 대시보드 / 입출력·리포트 / 인증·권한. 스토리 에픽 및 예상 유닛 구조와 그대로 정렬된다 (**권장** — Units Generation 단계의 분해가 자연스럽게 이어짐)

B) **도메인 엔티티 기준** — 엔티티 10개마다 모듈을 둔다. 대시보드처럼 여러 엔티티를 가로지르는 기능의 소속이 애매해진다

C) **기술 계층 기준** — controllers / services / repositories 폴더로 나누고 그 안에 전 기능을 담는다. 규모가 커지면 관련 코드가 흩어진다

## Question 6 — 입력 검증
입력 검증 스키마를 어디에 둘까요?

A) **Zod 스키마를 단일 정의하고 서버·클라이언트가 공유** — API 경계에서 검증하고 같은 스키마를 폼 검증에도 재사용한다 (**권장** — 필수값(FR-001), 점수 범위(FR-008), 날짜 순서(FR-011·FR-012) 규칙이 한 곳에만 존재)

B) **서버에서만 검증** — 클라이언트는 서버 응답의 오류 메시지만 표시한다. 구현이 단순하나 입력 피드백이 느리다

C) **계층별 개별 검증** — 폼과 API가 각자 검증 규칙을 갖는다

## Question 7 — 이력·알림 기록 방식
단계 변경 이력(append-only)과 알림 생성을 어떻게 처리할까요?

A) **애플리케이션 서비스에서 트랜잭션으로 명시 기록** — 단계 변경과 이력 기록을 하나의 트랜잭션으로 묶고, 알림도 같은 서비스에서 생성한다 (**권장** — 흐름이 코드에 드러나고 디버깅이 쉬움. 트랜잭션 경계가 명확해 이력 누락이 발생하지 않음)

B) **Prisma 미들웨어/확장으로 자동 기록** — 단계 필드 변경을 가로채 이력을 자동 생성한다. 호출부가 깔끔해지지만 동작이 암묵적이라 추적이 어렵다

C) **이벤트 기반** — 도메인 이벤트를 발행하고 핸들러가 이력·알림을 처리한다. 확장성은 좋으나 PoC 규모에는 과함

X) 기타 (아래 [Answer]: 뒤에 설명해주세요)

[Answer]: A

## Question 8 — 오류 처리 규약
도메인 오류를 어떻게 HTTP 응답으로 바꿀까요?

A) **도메인 오류 타입 + 단일 매핑 지점** — `ValidationError` / `NotFoundError` / `ForbiddenError` / `ConflictError` 등 도메인 오류를 정의하고, 한 곳에서 HTTP 상태코드와 응답 형식으로 매핑한다 (**권장** — US-026의 *"계정 존재 여부를 노출하지 않는 동일 메시지"* 같은 규칙을 한 곳에서 통제 가능)

B) **핸들러마다 개별 처리** — 각 API 핸들러가 try-catch로 직접 상태코드를 정한다

X) 기타 (아래 [Answer]: 뒤에 설명해주세요)
