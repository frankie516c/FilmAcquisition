# Requirements — U6 Acquisition Signals (인수 판단 근거)

**작성일**: 2026-07-26
**단계**: 🔵 INCEPTION — Requirements Analysis (증분)
**상태**: ✅ 승인 — Q-U6-1~5 답변 확정 (2026-07-26)
**기반**: `requirements.md` (FR-001~024, NFR-001~009)

> **증분 요구사항 문서입니다.** 기존 요구사항을 대체하지 않고 확장합니다.
> FR 번호는 FR-025부터, NFR은 NFR-010부터 이어갑니다.

---

## 1. 배경 — 왜 필요한가

현재 시스템은 **"무엇을 결정했는가"만 기록하고 "그 결정이 옳았는가"는 기록하지 않습니다.**

단계 이력(`StageTransition`)은 누가 언제 어느 단계로 옮겼는지 남기지만, **왜 옮겼는지**는
사유 메모 한 줄이 전부입니다. 재무 모델은 ROI를 계산하지만 그 기대 수익 숫자가 어디서
나왔는지는 어디에도 없습니다.

그 결과 사후 검토가 불가능합니다. 6개월 뒤 "이 작품을 왜 샀지?"를 물으면 답할 근거가 없고,
**판단 기준이 개선되지 않습니다.**

U6은 이 공백을 메웁니다. 목표는 "점수를 하나 더 만드는 것"이 아니라
**결정 시점의 근거를 검증 가능한 형태로 남기는 것**입니다.

## 2. 제안 대비 결정 사항

원 제안은 6개 항목과 3개 heat 위젯이었습니다. 검토 결과는 다음과 같습니다.

| 원 제안 | 결정 | 근거 |
|---|---|---|
| 1) 영화제 초청/수상/프리미어 | **부분 채택** — 기존 `FestivalRecord` 확장 | 초청·수상은 이미 구현됨. **프리미어 구분만 신규** |
| 2) 세일즈 에이전트 셀링 포인트 | **채택** | 현재 저장할 곳 없음 |
| 3) 해외 리뷰 톤·키워드 | **채택** — 독립 신호로 분리 | 현재 `FestivalRecord.criticalResponse` 자유 텍스트뿐. 영화제에 딸리지 않은 리뷰는 넣을 곳이 없음 |
| 4) 트레일러 반응·조회수·댓글 | **조건부 채택** — 시점 관측으로만 | 5절 D-1 참조 |
| 5) 유사작 국내외 성과 | **채택 — 최우선** | 6개 중 유일하게 반증 가능한 신호 |
| 6) 시사 메모·담당자 평가·스코어카드 | **기각 — 이미 존재** | `Evaluation`(4항목 + screeningDate/Venue/Attendees) + `Comment`가 이미 커버 |
| Festival / Critical / Market heat 위젯 | **채택 — 단, 점수 아님** | 5절 D-2 참조 |

**6번을 기각한 이유가 중요합니다.** 새 칸을 만들면 평가가 두 곳으로 갈라집니다.
담당자가 스코어카드에도 쓰고 새 칸에도 쓰면 두 값이 어긋나고, 어느 쪽이 진짜인지
아무도 모르게 됩니다. 이 시스템이 지켜온 **단일 정의 지점 원칙**(`financials.ts`가 ROI를
혼자 정의하는 것)이 깨집니다.

## 3. 범위

### 3.1 In Scope (Q-U6-5 = C — 근거 우선)
- 관측(Signal) 기록: 세일즈 포인트 · 해외 리뷰 · 트레일러 지표 · 바이어 관심 · 시장 메모
- 유사작(Comparable) 성과 기록과 유사 판단 기준 + KOBIS 조회 링크
- `FestivalRecord`에 프리미어 구분 추가
- 출처 등급(공개/준공개/내부)과 등급별 노출 통제
- 작품 상세의 **근거 탭**

### 3.1.1 다음 단위로 이월 (Q-U6-5 = C)
- **Heat 카드 3종** (FR-037~040) — 근거 데이터가 쌓인 뒤에 만드는 것이 맞습니다.
  요약할 대상이 없는 상태에서 요약 화면을 먼저 만들면 무엇을 요약해야 하는지 모른 채
  형태부터 정하게 됩니다.

### 3.2 Out of Scope (명시적 제외)
- **외부 시스템 자동 연동** — KOBIS·IMDb·YouTube API 크롤링 없음. 전량 수동 입력
- **감성 분석·NLP** — 리뷰 톤은 사람이 판정해 입력
- **Heat 종합 점수** — 5절 D-2에서 금지 규칙으로 명문화
- **예측 모델** — 유사작 데이터로 흥행을 추정하는 계산은 하지 않음. 근거를 나란히 보여줄 뿐
- **시장 리포트 본문 저장** — 10절 A-U6-3 참조

## 5. 핵심 설계 결정

### D-1. 신호는 필드가 아니라 **추가만 되는 관측**이다

**결정**: `Signal`은 생성만 가능하다. 수정·삭제 API를 두지 않는다.

**근거**: 사후 검토에서 필요한 것은 "지금 사실이 무엇인가"가 아니라
**"결정한 시점에 우리가 무엇을 알고 있었는가"**입니다.

칸 초청이 수상으로 바뀌는 그 **변화 자체가 신호**입니다. 현재 상태만 저장하면 그 정보가
사라집니다. 트레일러 조회수도 마찬가지입니다 — 3월의 120만과 7월의 120만은 완전히 다른
의미인데, 값을 덮어쓰면 구분할 수 없습니다.

**구현 방식**: `StageTransition`과 동일하게 **리포지토리 인터페이스에서 메서드를 없애**
컴파일 시점에 차단합니다. 잘못된 관측은 **철회 레코드**로 무효화하되 원본은 남깁니다
(BR-U6-002).

### D-2. Heat는 점수가 아니라 근거의 묶음이다

**결정**: Festival / Critical / Market heat에 **종합 점수를 만들지 않는다.** 이는 금지
규칙이며 FR-035로 명문화한다.

**근거**: 현재 `score.ts`는 4개 항목을 **단순 평균**합니다. 가중치가 없다는 것은 가중치
판단을 하지 않겠다는 선언이고, 최소한 정직합니다.

`Festival heat 82`는 다릅니다. 칸 경쟁부문과 선댄스 월드시네마를 한 숫자로 합치려면
가중치가 필요한데, 그 가중치는 아무도 검증할 수 없습니다. 그런데 **사람들은 그 숫자로
정렬합니다.** ROI는 반증 가능합니다 — 개봉하면 답이 나옵니다. Festival heat는 영원히
반증 불가능합니다.

| 표시 | 금지 |
|---|---|
| `칸 경쟁 · 감독상 · 월드프리미어` | `Festival heat 82` |
| `리뷰 7건 — 긍정 5 / 중립 2` | `Critical heat 71` |
| `셀링포인트 3 · 바이어 관심 2 · 유사작 4` | `Market heat 64` |

### D-3. 출처 등급은 신뢰도가 아니라 **법적 지위**의 문제다

**결정**: 모든 관측은 `PUBLIC` / `SEMI_PUBLIC` / `INTERNAL` 중 하나를 반드시 갖는다.
등급은 필드가 아니라 **레코드 속성**이다.

**근거**: 세 등급은 검증 가능성만 다른 게 아닙니다.

| 등급 | 예 | 위험 |
|---|---|---|
| `PUBLIC` | 영화제 공식 발표, 매체 리뷰, 공개 트레일러 | 없음. 재확인 가능 |
| `SEMI_PUBLIC` | 바이어 코멘트, 업계 인터뷰, 마켓 현장 대화 | 실명 귀속 기록이 유출되면 **관계 파탄·명예훼손** |
| `INTERNAL` | 소수 초청 시사 메모, 내부 평가 | 상당수가 **NDA 하에 관람**. 유출 시 세일즈 에이전트와의 거래 관계 종료 |

**통제 지점**: 이 시스템은 필드 단위 기본 차단 정책과 **단일 직렬화 게이트**를 이미 갖고
있어 감당할 수 있습니다. 실제 위험은 **CSV 내보내기**입니다 — 내부 메모가 CSV로 나가
메일에 첨부되는 순간 통제가 끝납니다. FR-033이 이를 막습니다.

> 믿게 만들기 때문입니다. 따라서 **입력 시점 경고 + 문서화된 운영 규칙**으로 명시하고,
> 자동 검증은 하지 않는다고 적습니다.

> **FR-043은 API 연동이 아닙니다.** 검색 URL 문자열을 조립할 뿐이며 외부 호출이 없습니다.
> 순수 함수로 `src/domain/`에 두면 테스트 가능합니다. 3.2절 Out of Scope와 충돌하지 않습니다.

### 7.1 `Signal` (신규)

### 7.2 `ComparableTitle` (신규)

| 속성 | 설명 | 필수 |
|---|---|---|
| `titleId` | 대상 작품 | ✅ |
| `comparableName` | 유사작명 | ✅ |
| `releaseYear` | 개봉연도 | ✅ |
| `basis` | 유사 판단 기준 — DIRECTOR / GENRE / COUNTRY / SCALE / OTHER (FR-032) | ✅ |
| `basisNote` | 기준 부연 | — |
| `domesticAdmissions` | 국내 관객수 | — |
| `overseasNote` | 해외 성과 (자유 서술) | — |
| `sourceGrade` / `sourceUrl` | 출처 | ✅ / 조건부 |
| `recordedById`, `createdAt` | — | ✅ |

**금액을 넣지 않았습니다.** 국내 관객수는 KOBIS 기준으로 검증 가능하지만 해외 매출은
환율·기간·집계처가 제각각이라 숫자로 두면 비교 불가능한 것을 비교하게 됩니다.

## 8. 권한

### 8.1 동작 권한 (`ACTION_POLICY` 추가분)

| Action | SCOUT | ANALYST | EXECUTIVE |
|---|---|---|---|
| `signal:create` | ✅ | ✅ | ❌ |
| `signal:retract` | ❌ | ✅ | ✅ |
| `comparable:write` | ❌ | ✅ | ❌ |

**Executive가 관측을 기록하지 않습니다.** 승인자가 근거를 직접 만들면 근거가 아니라
사후 정당화가 됩니다. 다만 잘못된 관측을 철회할 권한은 갖습니다.

### 8.2 필드 권한 (`FIELD_POLICY` 추가분)

`ComparableTitle`, `FestivalRecord.premiereStatus`는 `kind: "open"`입니다 — 전부 공개 정보입니다.

`Signal`도 `open`입니다. **필드 단위로 막을 것이 없기 때문입니다** — 통제 대상은 필드가
아니라 **레코드 전체**이고, 그건 8.3절이 담당합니다.

### 8.3 ⚠️ 행 단위 권한 — 이 시스템에 처음 등장합니다

**Q-U6-1 = B(작성자 본인 포함)는 기존 권한 구조로 표현할 수 없습니다.**

현재 정책 함수의 서명은 이렇습니다.

```
canReadField(role: Role, entity: string, field: string): boolean
```

**사용자 ID가 없습니다.** 역할만 받습니다. 직렬화 게이트도 마찬가지입니다. 즉 "이 관측을
쓴 사람이 지금 요청한 사람인가"를 판정할 자리가 **어디에도 없습니다.**

Scout가 자기가 기록한 내부 시사 메모를 못 보는 건 말이 안 되므로 B가 옳은 답입니다.
다만 그 대가로 **행 단위 권한이라는 새 개념이 시스템에 들어옵니다.**

**결정: 정책 테이블을 확장하지 않고, 조회 자체를 제한합니다.**

| 안 | 판정 |
|---|---|
| `canReadField`에 `userId`를 추가 | ❌ 12개 Action과 8개 엔티티 정책 전체의 서명이 바뀝니다. 행 단위가 필요한 곳은 `Signal` 하나뿐인데 대가가 너무 큽니다 |
| 서비스 계층에서 조회 후 걸러내기 | ❌ 거르지 않는 경로를 새로 만들면 조용히 새어 나갑니다. **실패가 안전하지 않은 방향** |
| **리포지토리 질의의 `WHERE`에 조건을 넣기** | ✅ **채택.** 걸러지지 않은 `Signal` 배열이 애초에 메모리에 존재하지 않습니다 |

**BR-U6-005**: `Signal` 리포지토리는 **`ctx`를 받지 않는 조회 메서드를 제공하지 않는다.**
`findAll(titleId)` 같은 메서드가 존재하면 언젠가 누군가 그것을 씁니다.
`StageTransition`에서 수정 메서드를 없애 append-only를 강제한 것과 같은 방식입니다 —
**규율이 아니라 부재로 강제합니다.**

```
WHERE titleId = ?
  AND ( sourceGrade <> 'INTERNAL'
        OR ?role IN ('ANALYST','EXECUTIVE')
        OR recordedById = ?userId )
```

**FR-033(내보내기 차단)은 이것과 별개입니다.** Analyst는 `INTERNAL` 관측을 화면에서
볼 수 있지만 CSV로는 내보낼 수 없습니다. 조회 권한과 반출 권한이 다릅니다 — 유출은
화면이 아니라 파일에서 일어납니다.

> **주의**: `RELATION_MAP.Title`에 `signals`, `comparableTitles`를 등록하지 않으면
> 직렬화 게이트가 통째로 차단합니다. 이는 의도된 안전 실패이며, 등록 누락 시
> "안 보인다"는 눈에 띄는 버그로 나타납니다.

## 9. 비기능 요구사항

### NFR-010 — 출처 등급 유출 방지

- `INTERNAL` 관측은 내보내기 경로에서 **직렬화 게이트 이전 단계**에 제외한다.
  게이트 이후 필터링은 파일 생성 코드가 원본 배열을 참조할 여지를 남긴다
- 통합 테스트로 3역할 × 3내보내기형식 = **9건 전수 검증**한다
- 등급 미지정 관측은 저장 자체를 거부한다 (`NOT NULL` + 기본값 없음).
  기본값을 두면 실수로 `PUBLIC`이 붙는다
