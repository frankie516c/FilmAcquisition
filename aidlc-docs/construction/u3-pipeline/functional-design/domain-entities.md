## 2. `StageTransition` — 이 프로젝트에서 가장 제약이 강한 테이블

### 2.1 append-only의 3중 표현

수정·삭제를 막기 위해 세 층위에서 표현했습니다.

| 층위 | 방식 | 차단 시점 |
|---|---|---|
| **타입** | 리포지토리에 `update`·`delete` 메서드를 **정의하지 않음** | 컴파일 |
| **스키마** | `updatedAt` 필드를 두지 않음 | — (의도 표현) |
| **코드 리뷰** | 설계 위반 판정 #5 | 리뷰 |

**타입 차단이 핵심입니다.** 호출할 수단 자체가 없으면 실수로 호출할 수 없습니다.
런타임 검사나 DB 권한보다 앞선 지점에서 막힙니다.

**`updatedAt`을 두지 않은 것은 기능이 아니라 신호입니다.** 다른 모든 테이블에는 있는 필드가
여기만 없으면, 이 테이블이 수정을 전제하지 않는다는 사실이 스키마를 읽는 사람에게 드러납니다.

**DB 권한으로 막지 않은 이유**: 애플리케이션이 단일 DB 사용자로 접속하는 구성에서 테이블별
권한 분리는 관리 비용 대비 실효가 적습니다.

### 2.2 `fromStage`가 null인 레코드

작품당 정확히 1건 존재하며, 작품 생성 시 함께 만들어집니다 (T3).

**이 레코드가 없으면** 체류 일수 계산의 시작점이 사라져 "총합 = 등록 후 경과 일수" 속성이
깨집니다. 그래서 생성이 트랜잭션으로 묶여 있습니다.

| 생성 경로 | `note` |
|---|---|
| 개별 등록 | `작품 등록` |
| CSV 가져오기 | `CSV 가져오기` |
| 시드 | `null` |

### 2.3 필드 결정

| 필드 | 결정 |
|---|---|
| `occurredAt` | `ctx.now` — DB의 `now()`가 아니라 **요청 시각**을 씁니다. 한 요청 안의 모든 계산이 같은 시각을 쓰게 하기 위함입니다 |
| `changedById` | `SetNull` — 사용자를 지워도 이력은 남습니다. 이력이 사라지면 체류 일수 불변식이 깨집니다 |
| `note` | 선택. 최대 500자. 사유를 남기지 않아도 전환은 성립합니다 |
| `createdAt` | 있음 (레코드 삽입 시각). `occurredAt`과 보통 같지만 시드에서는 다릅니다 |

### 2.4 인덱스

`(titleId, occurredAt)` — 이력 시간순 조회와 체류 일수 계산이 모두 이 순서를 요구합니다.

## 3. `Title.stage` — U3가 변경하는 유일한 필드

### 3.1 변경 경로가 하나뿐이다

`PipelineService.changeStage()` 외에는 `stage`를 바꾸는 경로가 없습니다.

- `updateTitle()`은 `stage`를 스키마에서 아예 받지 않습니다 (BR-U2-004)
- 작품 생성 시에는 `DISCOVERY` 고정입니다

**이유**: 단계 변경은 반드시 이력과 함께 일어나야 합니다. 경로가 여럿이면 그중 하나가
이력을 빠뜨립니다.

### 3.2 7단계 열거형

`DISCOVERY → SCREENING → EVALUATION → OFFER → NEGOTIATION → CLOSED_WON | REJECTED`

**순서는 표시용일 뿐 제약이 아닙니다.** 건너뛰기와 되돌리기가 모두 허용됩니다 (US-006).

**종료 상태**(`CLOSED_WON`·`REJECTED`)는 병목 계산에서만 특별 취급됩니다 — 계속 머무는 것이
정상이라 항상 평균이 가장 커져 지표가 무의미해지기 때문입니다.

## 4. 파생 데이터 — 저장하지 않음

| 값 | 저장 여부 | 사유 |
|---|---|---|
| 단계별 체류 일수 | ❌ 조회 시 계산 | 현재 단계의 체류 일수는 매일 늘어납니다. 저장하면 매일 갱신해야 합니다 |
| 병목 단계 | ❌ 조회 시 계산 | 전 작품에 걸친 집계라 어느 한 레코드에 속하지 않습니다 |
| 단계 진입 시각 | ❌ 이력에서 유도 | 이력이 이미 그 정보를 담고 있습니다. 중복 저장은 어긋날 여지만 만듭니다 |

> **성능상 재고 여지가 있습니다.** 작품 500건이면 매 대시보드 요청마다 2,000~3,000건의
> 이력을 메모리로 가져와 계산합니다. 다만 체류 일수를 이력에 저장하면 **append-only 테이블에
> 파생값을 넣는 것**이라 설계 재검토가 필요합니다 (performance-test-instructions.md 5절).
