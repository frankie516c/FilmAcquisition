### 4.1 결함 11번이 드러낸 테스트 구조의 사각지대

10번을 고칠 때 **표시 경로만 고치고 입력 경로를 확인하지 않았습니다.**

`note`의 경로는 이랬습니다.

| 구간 | 상태 |
|---|---|
| `StageTransition.note` 스키마 | ✅ 있음 |
| `changeStage(ctx, id, toStage, note?)` 서비스 | ✅ 받음 |
| `POST /api/pipeline/{id}/stage` 검증 스키마 | ✅ 받음 |
| 작품 상세 이력 행 렌더링 | ✅ 표시함 (10번에서 고침) |
| **칸반 화면의 입력 UI** | ❌ **없음** |

즉 **양 끝은 멀쩡한데 중간이 끊겨** 사용자가 입력한 사유가 존재할 수 없었습니다.
`note`는 `작품 등록`과 `CSV 가져오기` 두 자동 문구를 빼면 항상 `null`이었습니다.

**통합 테스트는 이걸 잡을 수 없습니다.** `pipeline.test.ts`는 API에 `note`를 직접 실어
보내고 저장·표시를 확인합니다 — API 계약은 정상이므로 통과합니다. 화면에 그 값을 보낼
수단이 있는지는 **아무도 검사하지 않습니다.**

**구조적 한계이지 부주의가 아닙니다.** 현재 테스트 계층은 도메인(순수 함수)과
HTTP(통합)뿐이고 **UI 배선을 검사하는 계층이 없습니다.** 10·11번이 연달아 사람이 화면을
봐야만 드러난 이유입니다.

→ 5절 4번 항목(E2E 도입)의 근거가 이것입니다. 이 두 건은 Playwright 시나리오 하나면
둘 다 잡혔습니다.
