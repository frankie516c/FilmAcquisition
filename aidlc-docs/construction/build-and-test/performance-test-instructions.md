## 3. 우려했던 지점은 문제가 되지 않았다

개정 전 문서는 다음 네 곳이 "전 건을 애플리케이션 메모리로 가져오므로 비선형으로 나빠질 수
있다"고 지적했습니다. **실측 결과 그 우려는 현실화되지 않았습니다.**

| 지점 | 예상 | 실측 |
|---|---|---|
| `getPipelineOverview` — 전 이력 로딩 | 비선형 악화 | 24→500편(20.8배)에 **2.2배** |
| `getUpcomingDeadlines` — 전 건 조회 후 필터 | 〃 | 대시보드에 포함, 위와 동일 |
| `getPortfolioComposition` — 메모리 집계 | 〃 | 〃 |
| `exportTitles` — 두 번 조회 후 결합 | 〃 | 27→53ms (**2.0배**) |

### 왜 예상이 빗나갔는가

**데이터가 20.8배 늘었는데 응답은 2~3.6배만 늘었습니다.** 즉 증가가 **선형보다 완만**합니다.

이 규모에서는 요청당 고정 비용(Next.js 렌더링, 커넥션 획득, 직렬화)이 지배적이고, 실제
데이터 처리(1,827건의 이력을 순회하며 체류 일수 계산)는 아직 작은 비중입니다.

**다만 이것은 "메모리 로딩이 좋은 설계"라는 뜻이 아닙니다.** 요구 규모의 2배(1,000편)에서
작품 목록이 349ms로 예산의 70%를 쓰기 시작합니다. 대략 **1,400~1,500편 부근에서 500ms를
넘길 것으로 보입니다.** 요구사항이 그 이상으로 커지면 5절의 개선이 필요합니다.

## 4. 재현 방법

측정 도구가 저장소에 포함되어 있습니다.

```bash
# 1) 서버 기동
node --env-file=.env node_modules/next/dist/bin/next start -p 3100

# 2) 목표 규모로 증량 (기존 데이터는 유지, 부족분만 생성)
npx tsx --env-file-if-exists=.env scripts/bulk-titles.ts 500

# 3) 응답 시간 측정
npx tsx --env-file-if-exists=.env scripts/measure.ts 20

# 4) CSV 가져오기 측정
npx tsx --env-file-if-exists=.env scripts/measure-import.ts 500

# 5) 원상복구 — "[대량]"으로 시작하는 작품만 삭제
npx tsx --env-file-if-exists=.env scripts/bulk-titles.ts --clean
```

### 4.1 측정 도구의 설계

| 항목 | 방식 | 이유 |
|---|---|---|
| 워밍업 | 첫 요청은 버림 | 서버 초기화·커넥션 풀 워밍업이 섞여 실제보다 크게 나옴 |
| 계측 범위 | **본문 수신 완료까지** | 헤더만 받고 끝내면 렌더링·직렬화 비용이 빠짐 |
| p95 | 정렬 후 `ceil(n×0.95)−1` | — |
| 난수 | **고정 시드** | 실행마다 같은 데이터가 나와야 비교가 가능 |
| 정리 표식 | `titleKo`가 `[대량]`으로 시작 | 시드 데이터와 사용자 데이터를 건드리지 않음 |

### 4.2 생성되는 데이터 (500편 기준)

| 항목 | 건수 |
|---|---|
| 작품 | 476 (기존 24 + 476 = 500) |
| 단계 이력 | 1,827 (작품당 평균 3.8건) |
| 딜 | 232 |
| 재무 | 145 |
| 판권 | 67 |

**이력을 작품당 평균 3.8건 만드는 것이 중요합니다.** 이력이 1건뿐이면 체류 일수 계산이
실제 부하를 반영하지 못해 측정이 무의미해집니다.

## 5. 규모가 더 커진다면 (현재는 불필요)

측정 없이 미리 최적화하지 마세요. 아래는 1,500편을 넘어설 때의 순서입니다.

1. **작품 목록 페이지네이션** — 가장 먼저 한계에 닿는 지점입니다. 전 건을 한 화면에 렌더링합니다
2. **DB에서 거르기** — `getUpcomingDeadlines`가 전 건을 가져와 메모리에서 필터링합니다.
   `where`에 기간 조건을 넣으면 전송량이 줄어듭니다
3. **집계를 DB로** — 포트폴리오 장르 분포를 `GROUP BY`로
4. **체류 일수 사전 계산** — 파이프라인 위젯이 가장 무겁습니다. 단, append-only 이력에
   파생값을 넣는 것이므로 **설계 재검토가 필요**합니다
5. **CSV 반영을 `createMany`로** — 현재 500건을 순차 생성해 805ms입니다. 아직 여유가 큽니다
6. **인덱스 점검** — `EXPLAIN ANALYZE`로 실제 사용 여부 확인
