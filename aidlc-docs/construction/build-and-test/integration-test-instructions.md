### 2.1 기본 테스트와 분리한 이유

`npm test`(단위·속성)에는 포함되지 않습니다. 통합 테스트는 **서버와 DB가 떠 있어야** 하므로,
섞으면 환경이 없는 곳에서 전부 실패해 정작 순수 로직의 회귀 신호까지 묻힙니다.

설정은 `vitest.integration.config.ts`에 분리했고 `fileParallelism: false`입니다 —
같은 데이터를 만지므로 병렬이면 서로의 상태를 깨뜨립니다.

### 2.2 테스트가 지키는 규칙

| 규칙 | 이유 |
|---|---|
| **역할은 로그인 응답의 `role`로 판정** | 이메일로 가정하면 실행 중 역할이 바뀌었을 때 거짓 실패합니다. 실제로 겪은 오진입니다 |
| 세 역할이 모두 확보되지 않으면 **즉시 중단** | 역할이 바뀐 채로 권한 테스트를 돌리면 결과가 무의미합니다 |
| 픽스처는 **자기가 만들고 자기가 지움** | `afterAll`에서 삭제합니다. 시드 데이터를 건드리지 않습니다 |
| BOM은 **바이트로** 검사 | `Response.text()`가 선두 BOM을 제거하므로 문자열로는 확인할 수 없습니다 |

### 2.3 환경변수 주의

테스트 대상 주소는 `FAD_BASE_URL`입니다. **`BASE_URL`을 쓰면 안 됩니다** — Vite가 이 이름을
`"/"`로 미리 정의해 요청 URL이 `//api/...`로 깨집니다. 실제로 겪은 문제입니다.

## 4. 자동화 설계에서 주의한 점

### 4.1 권한 매트릭스(S10)가 데이터를 만들지 않는 방법

허용된 역할까지 실제로 실행하면 매번 작품·딜이 생겨 정리가 번거롭습니다. 그래서:

- **차단 역할** → `403`이어야 한다 (데이터를 만들지 않으므로 안전)
- **허용 역할** → `403`이 **아니어야** 한다 (`404`·`400`이어도 권한 게이트는 통과한 것)

대부분의 케이스는 존재하지 않는 ID를 써서 `404`로 끝납니다. 예외는 **작품 등록** 하나로,
검증이 권한보다 먼저 실행되므로 차단 역할에서 `403`을 받으려면 본문이 유효해야 하고,
그러면 허용 역할에서는 실제로 생성됩니다. 생성분은 `afterAll`이 지웁니다.

### 4.2 역할을 바꾸는 테스트(S9)의 복구

`last-executive.test.ts`는 실제로 역할을 변경합니다. 복구가 실패하면 **이후 다른 테스트의
권한 검증이 전부 거짓 실패**하므로 이중으로 방어합니다.

1. `afterAll`에서 시작 시점의 역할로 되돌림
2. 마지막 테스트가 복구를 명시적으로 수행하고 **검증**

### 4.3 DB 격리는 여전히 없습니다

테스트가 자기 픽스처를 만들고 지우는 방식으로 우회합니다. 실행 중단 시 잔여 데이터가
남을 수 있으며, 이름이 `[통합테스트]`로 시작하므로 식별해 지울 수 있습니다.

본격적으로 하려면 테스트 전용 스키마와 트랜잭션 롤백이 필요합니다.
