# 섹션 B. 질문 (답변 필요)

## Question 1 — 세션 유지 방식 (Business Logic Modeling)
로그인 상태를 어떻게 유지할까요? US-026의 수용 기준은 *"브라우저를 완전히 종료한 뒤 다시 접속하면 세션이 만료되어 로그인 화면이 표시된다"* 입니다.

A) **httpOnly 세션 쿠키 + DB 세션 테이블** — 세션 ID만 쿠키에 담고 실제 세션은 DB에 저장한다. 쿠키에 만료 시각을 지정하지 않으면(session cookie) 브라우저 종료 시 사라진다. 역할 변경이 **즉시 반영**된다 (**권장** — US-028의 *"역할 변경이 즉시 반영되어 다음 요청부터 새 역할의 권한이 적용된다"* 를 만족하려면 매 요청마다 현재 역할을 읽어야 함)

B) **서명된 JWT를 세션 쿠키에 저장 (무상태)** — DB 조회가 없어 가볍지만, 토큰에 역할이 박혀 있어 **역할을 변경해도 재로그인 전까지 이전 권한이 유지된다.** US-028의 즉시 반영 기준을 만족하지 못한다

C) **NextAuth(Auth.js) 등 라이브러리 사용** — 검증된 구현을 쓰지만 PoC에 비해 설정 표면이 넓고, 커스텀 RBAC를 얹는 작업이 별도로 필요하다

## Question 2 — 비밀번호 처리와 계정 발급 (Business Rules)
비밀번호를 어떻게 다루고, Executive가 계정을 만들 때 초기 비밀번호를 어떻게 정할까요?

A) **argon2id 해시 + Executive가 초기 비밀번호를 직접 지정** — 계정 생성 시 Executive가 비밀번호를 입력해 사용자에게 전달한다. 최초 로그인 시 변경 강제는 하지 않는다 (**권장** — PoC 규모에서 가장 단순하고, 비밀번호 변경 흐름이라는 별도 스토리를 만들지 않아도 됨)

B) **argon2id + 임시 비밀번호 자동 생성 + 최초 로그인 시 변경 강제** — 실무에 가깝지만 비밀번호 변경 화면·API·상태 플래그가 추가로 필요하다. US-028에 없는 요구사항이 늘어난다

C) **bcrypt 해시 + Executive가 직접 지정** — argon2 대신 bcrypt. 더 널리 쓰이지만 현재 권장 알고리즘은 argon2id다

## Question 3 — 금액 저장 타입 (Domain Model) ★ 중요
금액을 어떤 타입으로 저장할까요? requirements.md는 "KRW 정수(원 단위)"로만 정하고 자릿수는 정하지 않았습니다.

**문제**: PostgreSQL의 4바이트 정수(`Int`)는 최대 **약 21억(2,147,483,647)** 입니다. 영화 판권 MG는 대개 이 범위 안이지만, **P&A 예산과 예상 매출은 쉽게 넘어갑니다** (예: 예상 매출 300억 원). 재무 계산(D1)의 총 인수비용·손익분기도 같은 범위를 씁니다.

A) **8바이트 정수(`BigInt` → PostgreSQL `int8`)** — 최대 약 922경 원. 오버플로 걱정이 없다. 다만 JavaScript의 `BigInt`는 JSON으로 직접 직렬화되지 않으므로 **직렬화 게이트(X2)에서 문자열로 변환**해 내보낸다 (**권장** — 어차피 모든 응답이 X2를 통과하므로 변환 지점이 이미 하나로 모여 있고, 여기에 규칙을 한 줄 추가하면 됨)

B) **4바이트 정수(`Int`)** — 구현이 가장 단순하고 JSON 직렬화 문제가 없다. 대신 21억을 넘는 값 입력 시 저장에 실패하며, 검증에서 상한을 막아야 한다

C) **`Decimal`** — 정밀도 손실이 없고 큰 값도 다루지만, KRW는 소수점이 없어 소수 자릿수 관리가 불필요한 부담이 된다

X) 기타 (아래 [Answer]: 뒤에 설명해주세요)

[Answer]: A (사용자 "권장안대로" 응답)

## Question 4 — 열거형 마스터 데이터 (Domain Model)
장르·등급·영토·제작국가처럼 선택지가 정해진 항목을 어떻게 다룰까요?

A) **코드 상수로 고정 + DB에는 문자열 코드 저장** — 장르·등급·영토 목록을 코드에 상수로 정의하고 DB에는 코드값을 저장한다. 화면 표시명은 코드에서 매핑한다 (**권장** — 마스터 데이터 관리 화면이라는 스토리가 없고, requirements.md 가정 A-5에서 "사용자 정의 영토는 지원하지 않는다"로 확정됨)

B) **DB 마스터 테이블로 관리** — 별도 테이블에 목록을 두고 시드로 채운다. 나중에 관리 화면을 붙이기 쉽지만, 지금은 그 화면이 범위 밖이라 조회 조인만 늘어난다

C) **자유 텍스트 입력** — 제약 없이 입력한다. 포트폴리오 위젯(US-019)의 장르별 집계가 표기 흔들림으로 부정확해진다

## Question 5 — 오류 응답 본문 형식 (Error Handling)
API 오류 응답의 본문 구조를 어떻게 할까요?

A) **`{ error: { code, message, fields? } }` 형태** — `code`는 기계 판독용 식별자(`VALIDATION_FAILED` 등), `message`는 한국어 사용자 메시지, `fields`는 검증 실패 시에만 필드별 사유 배열 (**권장** — 폼에서 필드별 오류를 표시하려면 `fields`가 필요하고, 클라이언트가 분기하려면 `code`가 필요함)

B) **`{ message }` 단일 필드** — 가장 단순하지만 폼에서 어느 필드가 틀렸는지 표시할 수 없어, US-001·US-009·US-013의 검증 수용 기준을 화면에서 만족하기 어렵다

C) **RFC 9457 Problem Details 표준** — `type`·`title`·`status`·`detail` 구조. 표준 준수가 이점이지만 PoC에서는 형식이 과하다

## Question 6 — 시드 데이터의 규모와 구성 (Business Scenarios)
US-031은 *"시드만으로 위젯 3종이 모두 의미 있는 값을 표시"* 하고 *"7일 이내 만료 오퍼가 최소 1건"* 이어야 한다고 요구합니다. 어느 규모로 만들까요?

A) **작품 24편 + 사용자 5명** — 7단계에 고르게 분포(단계당 2~5편), 장르 6종·국가 5종에 걸치되 **의도적으로 한 장르를 0건으로 비워** 라인업 갭 기능이 보이게 한다. 딜은 12편에, 판권은 계약체결 4편에, 재무는 8편에 부여. 만료 임박은 오퍼 2건(D-3, D-6)과 판권 1건(D-21) (**권장** — 위젯 3종이 모두 의미 있게 채워지는 최소 규모)

B) **작품 8편 + 사용자 3명** — 최소 구성. 빠르지만 포트폴리오 분포 차트가 빈약해 보이고 병목 단계 계산이 무의미해진다

C) **작품 100편 + 사용자 5명** — 성능 목표(500건 기준)에 가까운 규모로 확인 가능. 대신 시드 스크립트가 길어지고 데이터가 기계적으로 반복된다

X) 기타 (아래 [Answer]: 뒤에 설명해주세요)

## Question 7 — 인증 화면과 라우팅 흐름 (Frontend Components)
미인증 사용자가 접근했을 때의 동작과 로그인 후 진입점을 어떻게 할까요?

A) **미인증 시 `/login`으로 리다이렉트, 로그인 후 역할과 무관하게 `/dashboard`로 이동** — 헤더에 현재 사용자·역할·알림 아이콘·로그아웃을 두고, 역할에 따라 **메뉴 항목만 다르게** 표시한다 (**권장** — 화면 구조가 하나라 유지가 단순하고, 역할 차이는 메뉴와 버튼 노출로 드러남)

B) **역할별로 다른 첫 화면** — Scout는 칸반 보드, Analyst는 마감 임박, Executive는 대시보드로 보낸다. 개인화되지만 데모 시 계정을 바꿀 때마다 다른 화면이 나와 비교가 어렵다

C) **로그인 없이 볼 수 있는 공개 랜딩 페이지 + 로그인 버튼** — 포트폴리오 소개용으로는 좋지만 US-030·US-031에 없는 화면이 추가된다

## Question 8 — 속성 기반 테스트 실행 설정 (Data Flow / 검증)
PBT 17개 속성을 어떤 강도로 돌릴까요?

A) **속성당 100회 + 실패 케이스 자동 축소(shrinking) + 고정 시드** — 실패 시 재현 가능하도록 시드를 고정한다 (**권장** — fast-check 기본값이며 로컬 테스트 시간이 짧게 유지됨)

B) **속성당 1,000회** — 더 넓게 탐색하지만 테스트 시간이 10배가 되어 반복 개발이 느려진다

C) **속성당 100회 + CI에서만 1,000회** — 이상적이지만 CI 파이프라인이 범위 밖(requirements.md 4.2절)이라 적용할 곳이 없다

X) 기타 (아래 [Answer]: 뒤에 설명해주세요)
