## 2. `Title` — 구현하며 확정된 사항

### 2.1 중복을 UNIQUE로 막지 않는다

`(titleOriginal, productionYear)`에 UNIQUE 제약이 아니라 **일반 인덱스**를 걸었습니다.

**근거**: US-001의 수용 기준이 *"중복 가능성 경고가 표시되고, 기존 작품으로 이동하거나
**그대로 등록을 진행할 수 있다**"* 입니다. 리메이크와 동명이작이 실제로 존재하므로 차단이 아니라
경고여야 합니다.

**구현**: `findDuplicateCandidates()`가 등록 화면에서 원제·연도 입력이 끝날 때(`onBlur`) 미리
조회해 경고를 띄웁니다. 저장 자체는 막지 않습니다.

### 2.2 단계는 이 유닛에서 바꾸지 않는다

`updateTitle()`은 `stage` 필드를 **의도적으로 받지 않습니다.**

**근거**: 단계 변경은 이력이 함께 남아야 합니다(T1). 작품 수정 경로로도 단계를 바꿀 수 있으면
이력 없이 단계가 변하는 구멍이 생깁니다. 단계 변경은 `PipelineService.changeStage`만 담당합니다.

이 제약을 화면에도 적었습니다: *"파이프라인 단계는 여기서 바꿀 수 없습니다. 이력이 남지 않는
경로를 만들지 않기 위해 단계 변경은 칸반 보드에서만 가능합니다."*

### 2.3 담당자 기본값

`assigneeId`를 지정하지 않으면 **생성자 본인**이 담당자가 됩니다. 미배정 상태를 만들지 않기
위함이며, 화면에서 담당자가 비어 보이는 일이 없습니다.

### 2.4 배열 필드

`genres`(필수, 최소 1개)와 `cast`(선택)는 PostgreSQL 배열입니다.

> **이 두 필드가 실제 결함의 원인이었습니다.** 직렬화 게이트가 배열을 무조건 "미등록 관계"로
> 보고 차단해 모든 API 응답에서 사라졌습니다. 화면은 Prisma 결과를 직접 읽어 정상으로 보였고,
> API를 직접 호출해야만 드러났습니다. 게이트가 **객체 배열만** 관계로 보도록 수정했습니다.

## 3. `Evaluation` — 구현하며 확정된 사항

### 3.1 UNIQUE 제약을 두지 않는다

`(titleId, evaluatorId)`에 제약이 없습니다.

**근거**: US-009가 *"기존 평가를 덮어쓰지 않고 평가자별로 나란히 보존"* 을 요구합니다.
같은 평가자가 재관람 후 두 번째 평가를 남기는 것도 허용됩니다 — 시간이 지나 판단이 바뀌는 것은
정상이며, 그 변화 자체가 기록으로서 가치가 있습니다.

### 3.2 종합 점수를 저장하지 않는다

`Evaluation`에 계산된 점수 컬럼이 없습니다. 조회 시 `D6 ScoreCalculator`가 계산합니다.

**근거**: 저장하면 항목 점수와 종합 점수가 어긋날 수 있습니다. 계산 비용이 무시할 수준이라
저장할 이유가 없습니다.

### 3.3 평가 0건과 0점을 구분한다

`calculateOverallScore([])`는 `0`이 아니라 `null`을 반환하고, 화면은 `미평가`로 표시합니다.

**근거**: 0점은 "형편없다는 평가"이고 미평가는 "아직 안 봤다"입니다. 목록 정렬과 필터에서
전혀 다르게 다뤄져야 합니다.

## 4. `Comment` — 구현하며 확정된 사항

### 4.1 멘션 대상을 별도 테이블에 저장하지 않는다

본문에서 파싱해 알림을 생성하며, **알림 레코드가 곧 멘션의 기록**입니다.

**근거**: US-010~012 어느 수용 기준도 "이 코멘트가 누구를 멘션했는가"를 되묻지 않습니다.
필요해지면 `Notification`에서 `commentId`로 역조회할 수 있습니다.

**대가**: 코멘트를 수정해 멘션을 바꿔도 알림은 갱신되지 않습니다. 현재 수정 기능이 화면에
없어 문제가 되지 않지만, 수정을 붙인다면 이 지점을 다시 봐야 합니다.

### 4.2 소유권으로 수정·삭제를 판정한다

동작 권한(역할)이 아니라 `authorId === ctx.userId`로 판정합니다. 역할이 무엇이든 남의 코멘트는
건드릴 수 없고, 자기 것은 누구나 지울 수 있습니다.

### 4.3 작성자 삭제 시 코멘트는 남는다

`authorId`가 `SetNull`이라 사용자를 지워도 코멘트는 보존되고 `(삭제된 사용자)`로 표시됩니다.

**근거**: 논의 맥락이 사람의 퇴사로 사라지면 안 됩니다. `Evaluation`·`StageTransition`도 같습니다.

## 5. `FestivalRecord` — 구현하며 확정된 사항

| 결정 | 근거 |
|---|---|
| `isAward` 불리언 + `awardName` 문자열 | 초청과 수상을 한 테이블로 다룹니다. `isAward=false`면 `awardName`은 의미 없습니다 |
| 연도 내림차순 표시 | US-003의 수용 기준. 인덱스 `(titleId, year)`로 지원 |
| 0건이어도 정상 | 영화제 이력이 없는 작품이 다수입니다. 빈 상태가 오류가 아닙니다 |

## 6. cascade 정리 (U2 관점)

```
Title 삭제
 ├─ FestivalRecord   Cascade  → 함께 삭제
 ├─ Evaluation       Cascade  → 함께 삭제
 ├─ Comment          Cascade  → 함께 삭제
 │   └─ Notification Cascade  → 멘션 알림도 함께 삭제
 └─ StageTransition  Cascade  → 함께 삭제

User 삭제
 ├─ Evaluation.evaluatorId  SetNull  → 평가는 보존
 └─ Comment.authorId        SetNull  → 코멘트는 보존
```

**방향이 다른 이유**: 작품이 사라지면 그 작품에 대한 평가는 의미가 없습니다. 사람이 떠나도
그가 남긴 판단은 의미가 있습니다.
