# Business Rules — U2 Title & Evaluation

**작성일**: 2026-07-26
**단계**: 🟢 CONSTRUCTION — U2 Functional Design

> ⚠️ **as-built 기록입니다.** 구현 중 확정된 규칙을 정리한 것이며 구현 전 설계서가 아닙니다.

규칙 ID는 `BR-U2-nnn`. U1이 정한 공통 규칙(검증·오류·표기·권한)은 여기서 되풀이하지 않습니다.

---

## 1. 작품 관리

### BR-U2-001 — 작품 등록 권한
**출처**: 권한 매트릭스 1번, US-001

`title:write`는 **SCOUT 전용**입니다. Analyst와 Executive는 403입니다.

**검증됨**: SCOUT 201 / ANALYST 403 / EXECUTIVE 403

### BR-U2-002 — 등록 시 초기 단계와 최초 이력 (트랜잭션 T3)
**출처**: FR-001, FR-006

작품을 만들면 반드시 다음 두 가지가 **하나의 트랜잭션**으로 일어납니다.

1. `Title` 생성, `stage = DISCOVERY`
2. `StageTransition` 생성, `fromStage = null`, `toStage = DISCOVERY`, `note = "작품 등록"`

**묶는 이유**: 이력의 시작점이 없으면 체류 일수 계산의 기준이 사라져 "총합 = 등록 후 경과 일수"
속성이 깨집니다. `fromStage`가 `null`인 레코드는 작품당 정확히 1건입니다.

**검증됨**: 등록 직후 `transitions=1`, `fromStage IS NULL` 확인.
CSV 가져오기 경로도 동일하되 `note = "CSV 가져오기"`.

### BR-U2-003 — 중복은 차단이 아니라 경고
**출처**: US-001

원제와 제작연도가 같은 작품이 있어도 **등록을 막지 않습니다.** 경고를 보여주고 기존 작품으로
이동할 선택지를 줄 뿐입니다.

**근거**: 리메이크와 동명이작이 실제로 존재합니다. 차단하면 정당한 등록이 불가능해집니다.

**원제가 없으면 중복 검사를 하지 않습니다.** 한국어 제목만으로는 동명이작과 중복 입력을
구분할 수 없기 때문입니다.

### BR-U2-004 — 수정 경로로 단계를 바꿀 수 없다
**출처**: FR-005, FR-006

`PATCH /api/titles/{id}`는 `stage`를 받지 않습니다. 요청에 넣어도 무시됩니다.

**근거**: 이력이 남지 않는 단계 변경 경로를 만들지 않기 위함입니다. BR-U2-002가 보장하는
불변식이 이 규칙 없이는 깨집니다.

### BR-U2-005 — 삭제는 하위 데이터를 함께 지운다 (트랜잭션 T2)
**출처**: US-002

작품을 지우면 평가·코멘트·이력·딜·판권·재무가 스키마의 `onDelete: Cascade`로 함께 삭제됩니다.
삭제 자체는 트랜잭션 안에서 수행해 부분 삭제 상태를 만들지 않습니다.

**화면 규약**: 하위 데이터가 있으면 확인 문구가 달라집니다 —
*"평가·코멘트·이력·딜이 함께 삭제됩니다. 되돌릴 수 없습니다."*
없으면 *"되돌릴 수 없습니다."* 만 표시합니다. 사용자가 잃을 것의 크기를 알고 결정하게 합니다.

### BR-U2-006 — 담당자 기본값
지정하지 않으면 생성자 본인이 담당자가 됩니다. 미배정 상태를 만들지 않습니다.

## 2. 검색과 필터

### BR-U2-007 — 검색 대상
**출처**: US-004

제목(`titleKo`)과 원제(`titleOriginal`)를 **대소문자 무시 부분 일치**로 검색합니다.
감독·시놉시스는 검색 대상이 아닙니다.

**근거**: US-004의 수용 기준이 *"제목 또는 원제에 해당 문자열을 포함한 작품"* 으로 한정합니다.

### BR-U2-008 — 필터 상태는 URL에 있다
**출처**: US-004

단계·검색어 등 필터는 쿼리 문자열로 표현되며, 컴포넌트 상태에 두지 않습니다.

**근거**: 수용 기준이 *"새로고침하거나 해당 URL을 다른 사용자에게 전달하면 동일한 필터 조건이
그대로 복원된다"* 입니다. 상태로 관리하면 이 두 가지가 모두 깨집니다.

## 3. 평가

### BR-U2-009 — 평가 등록 권한
**출처**: 권한 매트릭스 3번

`evaluation:write`는 **SCOUT 전용**입니다. Analyst·Executive는 읽을 수만 있습니다.

**근거**: 평가는 작품을 직접 본 사람이 남기는 기록입니다. 금액을 다루는 Analyst가 평가까지
하면 평가와 재무 판단의 분리라는 전제가 무너집니다(가정 A-1과 같은 맥락).

**검증됨**: SCOUT 201 / ANALYST 403 / EXECUTIVE 403

### BR-U2-010 — 평가는 덮어쓰지 않고 쌓인다
**출처**: US-009

같은 작품·같은 평가자라도 새 평가를 추가합니다. 기존 평가를 수정하지 않습니다.

### BR-U2-011 — 점수 범위
네 항목(작품성·상업성·화제성·타깃 적합성) 모두 **1~5 정수**입니다. 0·6·소수는 400입니다.

**검증됨**: `artistry=6` → `400 {"path":"artistry","code":"TOO_BIG"}`

### BR-U2-012 — 미평가와 0점의 구분
**출처**: US-010

평가 0건이면 종합 점수는 `null`이고 화면은 `미평가`로 표시합니다. **0점으로 계산하지 않습니다.**

## 4. 코멘트와 멘션

### BR-U2-013 — 코멘트 작성은 전 역할
**출처**: 권한 매트릭스 4번, US-011

Scout·Analyst·Executive 모두 작성할 수 있습니다. 조회 전용인 Executive에게 허용된 유일한
쓰기 동작입니다.

**근거**: 경영진이 확인을 요청할 통로가 필요하고, 그 요청이 작품에 붙어 남아야 합니다.

### BR-U2-014 — 수정·삭제는 소유권으로 판정
**출처**: US-011

`authorId === ctx.userId`일 때만 가능합니다. 역할과 무관합니다. 타인 것은 403입니다.

### BR-U2-015 — 멘션 파싱 규칙
**출처**: US-010

`@` 뒤에서 **공백 또는 문장부호 전까지**를 이름으로 봅니다.
정규식: `/@([^\s@.,!?;:()[\]{}'"]+)/g`

**한글 이름을 전제한 규칙입니다.** `@이분석,` 처럼 쉼표가 붙어도 `이분석`으로 인식됩니다.
같은 사람을 여러 번 언급해도 중복 제거되어 알림은 1건입니다.

**이름이 정확히 일치해야 합니다.** 부분 일치나 유사도 매칭을 하지 않습니다 — 잘못된 사람에게
알림이 가는 것이 알림이 안 가는 것보다 나쁩니다.

### BR-U2-016 — 멘션 알림 생성 (트랜잭션 T4)
**출처**: US-010, US-012

코멘트 생성과 알림 생성을 **하나의 트랜잭션**으로 묶습니다.

| 대상 | 알림 |
|---|---|
| 본문에 언급되고 실제로 존재하는 사용자 | 생성 |
| **작성자 본인** | **생성하지 않음** |
| 존재하지 않는 이름 | 무시 (오류 아님) |

**작성자를 제외하는 이유**: 자기가 쓴 글을 자기에게 알릴 이유가 없습니다.

**존재하지 않는 이름을 오류로 만들지 않는 이유**: 코멘트에 `@`가 우연히 들어갈 수 있고
(이메일 주소 등), 그것 때문에 코멘트 작성이 실패하면 안 됩니다.

**검증됨**: `@이분석 @최경영` 작성 → 두 계정에만 각 1건, 작성자 0건, 미언급자 0건

### BR-U2-017 — 코멘트 표시 순서
최신순입니다. 인덱스 `(titleId, createdAt)`로 지원합니다.
