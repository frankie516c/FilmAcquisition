# Business Logic Model — U1 Foundation & Auth

**작성일**: 2026-07-25
**단계**: 🟢 CONSTRUCTION — U1 Functional Design

순수 도메인 모듈 6종의 알고리즘, 직렬화 게이트의 동작, 인증 흐름, 시드 명세, PBT 설정을 정의한다.
**기술 중립**: 특정 라이브러리 API가 아니라 계산 규칙과 경계 조건을 기술한다.

## 1. 공통 기반 — 달력일 인덱스

`D2`(체류 일수)와 `D3`(D-day)가 공유하는 기반 개념이다.

### 1.1 정의

```
dayIndex(instant) = Asia/Seoul 기준으로 해당 순간이 속한 날짜의, 에포크(1970-01-01)로부터의 일 수
```

- 시각(시·분·초)은 결과에 영향을 주지 않는다. `2026-07-25 00:01`과 `2026-07-25 23:59`의 `dayIndex`는 같다
- 서버 시간대나 사용자 브라우저 시간대와 무관하게 항상 **Asia/Seoul**로 계산한다 (BR-U1-020)

### 1.2 이 정의가 중요한 이유

두 모듈의 PBT 속성이 **이 정의 위에서만 성립**한다.

| 속성 | 성립 근거 |
|---|---|
| `D2` P2 — 체류 일수 총합 = 등록 후 경과 일수 | 구간 경계가 인접 구간과 공유되므로 차분의 합이 **정확히 망원 급수로 상쇄**된다: `(d₁−d₀) + (d₂−d₁) + ... + (dₙ−dₙ₋₁) = dₙ − d₀`. 만약 각 구간을 "시각 차이 ÷ 24시간 후 내림"으로 계산하면 구간마다 버려지는 나머지가 쌓여 총합이 어긋난다 |
| `D3` P2 — 만료일 하루 증가 시 D-day 정확히 1 증가 | 정수 인덱스의 차이이므로 서머타임·윤초·시각 차이의 영향을 받지 않는다 |
| `D3` P3 — 시각 차이가 결과에 영향 없음 | 정의상 자명 |

> 이 한 가지 정의가 8개 PBT 속성(D2의 4개 + D3의 4개)의 근거다.

## 2. D1 — FinancialCalculator (재무 계산)

**출처**: FR-013, US-016 · **NFR-008의 단일 정의 지점**

### 2.1 산식

| 항목 | 산식 | 타입 |
|---|---|---|
| 총 인수비용 | `offerAmount + paAndBudget + otherCosts` | `bigint` |
| 예상 손익 | `expectedRevenue − 총 인수비용` | `bigint` (음수 가능) |
| 손익분기 매출 | `총 인수비용` | `bigint` |
| ROI (%) | `(예상 손익 ÷ 총 인수비용) × 100` | `number` 또는 `null` |

### 2.2 `offerAmount` 선택 규칙

입력의 `offerAmount`는 다음 우선순위로 정한다.

1. `Deal.minimumGuarantee`가 있으면 그 값
2. 없으면 `Deal.offerAmount`
3. 둘 다 없으면 `0`

> **근거**: MG(최소보증금)는 실제로 지급이 확정된 금액이므로, 있다면 그것이 인수비용이다. 오퍼 금액은 아직 협상 중인 제시액이다.

### 2.3 ROI 계산의 정밀도 처리

ROI는 백분율이므로 `bigint`가 아닌 `number`로 반환한다. 그러나 `bigint`를 `number`로 먼저 변환하면 큰 값에서 정밀도가 손실된다.

**계산 순서 (정수 연산을 최대한 유지)**

```
1. totalCost === 0n  →  null 반환 (아래 2.4)
2. scaled = (expectedProfit × 10000n) / totalCost      ← bigint 나눗셈 (소수점 이하 버림)
3. roiPercent = Number(scaled) / 100                    ← 소수 둘째 자리까지 보존
```

- `scaled`의 크기는 `10000 × (손익/비용)` 규모이므로 실무 범위에서 `number` 안전 정수 한계(약 9,007조)를 넘지 않는다
- 결과는 **소수 둘째 자리까지**, 버림(truncate) 처리. 반올림이 아니다
  > 반올림하지 않는 이유: ROI 표시는 판단 참고용이고, 버림은 항상 보수적(실제보다 낮게)이라 과대평가를 유발하지 않는다. 무엇보다 bigint 나눗셈이 이미 버림이므로 규칙이 일관된다.

### 2.4 0으로 나누기 처리

**출처**: US-016 (*"총 인수비용이 0이면 ROI는 `N/A`"*)

- `totalCost === 0n` → `roiPercent = null` 반환. **예외를 던지지 않는다**
- 화면은 `null`을 `N/A`로 표시한다
- 손익분기 매출은 `0`으로 정상 반환한다 (0원짜리 인수의 손익분기는 0원이 맞다)

### 2.5 PBT 속성 (5개)

| # | 속성 | 검증 방법 |
|---|---|---|
| P1 | `breakEvenRevenue === totalAcquisitionCost` | 임의 비음수 bigint 4개 조합 |
| P2 | `expectedRevenue === totalCost` 이면 `expectedProfit === 0n` 이고 `roiPercent === 0` | 비용을 먼저 생성한 뒤 매출을 그와 같게 설정 |
| P3 | `expectedRevenue` 증가 시 `expectedProfit`·`roiPercent` 비감소 | 임의 매출 쌍 (a ≤ b) 생성 후 비교 |
| P4 | `totalCost === 0n` 이면 `roiPercent === null` 이고 예외 없음 | 세 비용 항목을 모두 0으로 고정 |
| P5 | 모든 결과 금액이 정수 (`typeof === 'bigint'`) | 전 조합 |

**입력 생성기 범위**: `0n` ~ `10n ** 15n` (1000조). 실무 최대치를 크게 넘는 범위까지 검증한다.

## 3. D2 — DwellTimeCalculator (체류 일수)

**출처**: FR-006, US-008

### 3.1 구간 분할 알고리즘

**입력**: 작품 생성 시각 `createdAt`, 이력 목록 `transitions`(시간 오름차순), 현재 시각 `now`

```
1. transitions를 occurredAt 오름차순으로 정렬한다 (입력 순서를 신뢰하지 않는다)
2. 경계 시각 목록을 만든다:
       boundaries = [createdAt, t₁.occurredAt, t₂.occurredAt, ..., tₙ.occurredAt, now]
3. 각 구간 i (0 ≤ i < n+1)에 대해:
       stage     = i === 0 ? (첫 이력의 fromStage ?? DISCOVERY) : transitions[i-1].toStage
       enteredAt = boundaries[i]
       exitedAt  = (i === n) ? null : boundaries[i+1]     ← 마지막 구간은 진행 중
       days      = dayIndex(boundaries[i+1]) − dayIndex(boundaries[i])
4. 구간 배열을 반환한다
```

### 3.2 경계 조건

| 상황 | 처리 |
|---|---|
| 이력 0건 | 구간 1개. `stage = DISCOVERY`, `exitedAt = null`, `days = dayIndex(now) − dayIndex(createdAt)` |
| 같은 날 여러 번 이동 | 해당 구간들의 `days = 0`. 정상이며 P1(`days ≥ 0`)을 위반하지 않는다 |
| 종료 단계에서 되돌리기 | 특별 처리 없음. 되돌리기도 하나의 전환이므로 새 구간이 생긴다 |
| `now < 마지막 이력 시각` (시계 역행) | 발생하지 않는다고 가정한다. `occurredAt`은 항상 `ctx.now`로 기록되고 `now`도 같은 출처이므로 단조 증가한다 |

### 3.3 병목 단계 산출

**출처**: US-018 (파이프라인 위젯)

```
1. 전 작품의 구간 배열을 단계별로 모은다
2. 단계별 평균 days를 계산한다 (구간 수로 나눔, 작품 수가 아님)
3. 평균이 가장 큰 단계를 반환한다
4. 구간이 하나도 없으면 null
5. 동점이면 STAGE_ORDER에서 앞선 단계를 반환한다 (결정론적 결과 보장)
```

> **종료 단계(`CLOSED_WON`·`REJECTED`)는 병목 후보에서 제외한다.** 종료 상태는 계속 머무는 것이 정상이므로 항상 평균이 가장 커져 병목 지표가 무의미해진다.

### 3.4 PBT 속성 (4개)

| # | 속성 |
|---|---|
| P1 | 모든 구간의 `days ≥ 0` |
| P2 | `Σ days === dayIndex(now) − dayIndex(createdAt)` (**1.2절의 망원 급수 성질**) |
| P3 | 구간이 시간순으로 연속하고 겹치지 않는다 — `구간[i].exitedAt === 구간[i+1].enteredAt` |
| P4 | 이력 0건이면 구간 1개이고 그 `exitedAt === null` |

**입력 생성기**: `createdAt` 이후의 시각 0~20개를 임의 생성해 정렬 후 이력으로 사용. 같은 날 중복 시각을 포함하도록 생성한다.

## 4. D3 — DeadlineCalculator (D-day)

**출처**: FR-016, FR-019, US-020, US-024

### 4.1 D-day 계산

```
calculateDDay(baseDate, targetDate) = dayIndex(targetDate) − dayIndex(baseDate)
```

| 반환값 | 의미 |
|---|---|
| `0` | 오늘 만료 (D-0) |
| 양수 `n` | `n`일 남음 (D-n) |
| 음수 `−n` | `n`일 전에 만료됨 |

### 4.2 상태 분류

```
classifyDeadline(dDay, rangeDays):
    dDay < 0                →  'expired'      만료됨 (별도 강조 표시)
    0 ≤ dDay ≤ 7            →  'imminent'     임박
    7 < dDay ≤ rangeDays    →  'upcoming'     예정
    dDay > rangeDays        →  'out-of-range' 조회 범위 밖 (표시 안 함)
```

- `rangeDays`는 7·30·90 중 하나 (US-020의 범위 전환)
- `rangeDays = 7`이면 `'upcoming'` 구간이 비게 되는데 정상이다

### 4.3 알림 임계값 판정

**출처**: US-024

```
shouldNotify(dDay, thresholds) = thresholds.includes(dDay)
```

| 대상 | 임계값 | 결과 |
|---|---|---|
| 오퍼 만료 | `[7, 1]` | D-7과 D-1 두 시점에 알림 |
| 판권 만료 | `[30, 7]` | D-30과 D-7 두 시점에 알림 |

- **정확히 그 값일 때만** 알림한다 (`dDay <= 7`이 아니라 `dDay === 7`)
  > 이유: 범위 조건이면 D-7부터 D-0까지 매일 알림이 생성된다. 알림 중복 방지 키(`marker`)가 `D-7` 같은 임계값 문자열이므로, 정확 일치가 "임계값 하나당 알림 하나"를 보장한다
- 스캔이 하루 걸러 실행되지 않는 한 임계값을 건너뛰지 않는다. 로컬 PoC에서 기동 시 1회 + 일 1회 실행이므로 충분하다

### 4.4 PBT 속성 (4개)

| # | 속성 |
|---|---|
| P1 | `targetDate`와 `baseDate`가 같은 날이면 `dDay === 0` (시각이 달라도) |
| P2 | `targetDate`를 하루 늘리면 `dDay`가 정확히 1 증가 (선형성) |
| P3 | 두 입력의 시각(시·분·초)만 바꿔도 결과가 동일 (Asia/Seoul 달력일 기준) |
| P4 | `dDay < 0` 이면 `classifyDeadline`의 결과가 항상 `'expired'` (rangeDays와 무관) |

## 5. D4 — CsvSerializer (CSV 직렬화)

**출처**: FR-017, FR-018, US-021, US-022 · **RFC 4180 준수**

### 5.1 직렬화 규칙

| 규칙 | 내용 |
|---|---|
| 구분자 | 쉼표 `,` |
| 줄바꿈 | `CRLF` (`\r\n`) |
| 헤더 | 첫 행에 `columns`의 `header`를 순서대로 |
| 인용 조건 | 값에 **쉼표·큰따옴표·CR·LF** 중 하나라도 있으면 전체를 `"`로 감싼다 |
| 큰따옴표 이스케이프 | 값 내부의 `"`를 `""`로 치환 |
| `null`·`undefined` | 빈 필드로 출력 |
| `bigint` | 십진 문자열로 출력 |
| BOM | 파일 선두에 **UTF-8 BOM** 부착 |

> **BOM을 붙이는 이유**: BOM이 없으면 Microsoft Excel이 UTF-8 CSV를 시스템 인코딩으로 해석해 한글이 깨진다. US-022가 Excel 형식을 요구하므로 필요하다.
> **BOM이 왕복에 미치는 영향**: 파서가 **선두 BOM을 먼저 제거**한 뒤 처리한다. 이 처리가 없으면 첫 컬럼 헤더가 BOM 문자를 포함해 매칭에 실패하고 P1이 깨진다.

### 5.2 파싱 규칙

```
1. 선두 BOM이 있으면 제거한다
2. 문자를 순회하며 상태 기계로 파싱한다:
     - 인용 안: , → 필드 종료 · CRLF/LF → 행 종료 · " → 인용 시작
     - 인용 중: "" → 리터럴 " · " → 인용 종료 · 그 외(개행 포함) → 값에 축적
3. 줄바꿈은 CRLF와 LF를 모두 허용한다 (사용자가 편집한 파일 대응)
4. 헤더 행을 columns와 대조해 순서를 매핑한다
5. 각 데이터 행을 Record로 변환한다
6. 오류는 예외로 던지지 않고 errors 배열에 수집한다
```

### 5.3 오류 처리

**출처**: US-021 (*"오류 행 번호와 사유를 미리보기로 표시"*)

| 오류 | 코드 | 처리 |
|---|---|---|
| 헤더에 필수 컬럼 없음 | `MISSING_COLUMN` | 전체 실패 — 행 단위 처리가 불가능하므로 |
| 행의 필드 수가 헤더와 불일치 | `COLUMN_COUNT_MISMATCH` | 해당 행만 오류로 기록하고 계속 진행 |
| 인용이 닫히지 않고 파일 끝 도달 | `UNTERMINATED_QUOTE` | 해당 행만 오류. 남은 내용은 그 행의 값으로 취급 |

**어떤 경우에도 예외를 던지지 않는다.** 사용자 업로드 파일은 손상되어 있을 수 있고, 미리보기가 오류 목록을 보여줘야 하기 때문이다.

### 5.4 왕복 무손실의 성립 범위

**P1의 정확한 진술**:
> `columns`가 고정되어 있고 `rows`의 모든 값이 **문자열**일 때, `parseCsv(serializeToCsv(rows, columns), columns).rows === rows` 이다.

| 항목 | 왕복 결과 |
|---|---|
| 한글·이모지 | 보존 ✅ |
| 쉼표·큰따옴표·줄바꿈 포함 값 | 보존 ✅ |
| 앞뒤 공백 | 보존 ✅ (직렬화 계층은 `trim`하지 않는다. `trim`은 상위 검증 계층의 책임 — BR-U1-013) |
| 빈 문자열 `""` | 보존 ✅ |
| `null` | **보존되지 않음** — 빈 문자열로 복원됨 |

> **`null`이 왕복되지 않는 것은 CSV 형식의 본질적 한계**다. CSV에는 "빈 값"과 "값 없음"을 구분할 표현이 없다. 따라서 P1의 대상을 문자열 레코드로 한정한다. 상위 계층(가져오기 서비스)이 빈 문자열을 `null`로 정규화한다 (BR-U1-013).

### 5.5 PBT 속성 (4개)

| # | 속성 |
|---|---|
| P1 | 문자열 레코드에 대해 왕복 무손실 |
| P2 | P1이 한글·쉼표·큰따옴표·줄바꿈·이모지를 포함한 값에서도 성립 |
| P3 | 임의의 문자열 입력에 대해 `parseCsv`가 예외를 던지지 않는다 |
| P4 | `serializeToCsv`의 첫 행(BOM 제거 후)이 항상 `columns`의 `header` 순서와 일치 |

**입력 생성기**: 문자 집합에 `,` `"` `\r` `\n` 한글 이모지 공백을 명시적으로 포함시킨다. 무작위 유니코드에만 의존하면 이 문자들이 거의 생성되지 않아 P2가 실질적으로 검증되지 않는다.

## 6. D5·D6 및 X2

### 6.1 D5 — PipelineRules

```
STAGE_ORDER    = [DISCOVERY, SCREENING, EVALUATION, OFFER, NEGOTIATION, CLOSED_WON, REJECTED]
TERMINAL       = [CLOSED_WON, REJECTED]

isValidTransition(from, to):
    from === to        →  false   (같은 단계로의 이동은 변경이 아님)
    그 외              →  true
```

**출처**: US-006 (*"임의 단계로 변경 가능"*, *"종료 상태에서 이전 단계로 되돌리기 허용"*)

> 단계 건너뛰기와 되돌리기를 모두 허용하므로 실질적으로 `from === to`만 막는다. 승인 워크플로가 범위 밖(Q9=B)이므로 전이 제약을 두지 않는 것이 요구사항과 일치한다. `from === to`를 막는 이유는 아무 변화 없는 이력 레코드가 쌓이는 것을 방지하기 위함이다.

### 6.2 D6 — ScoreCalculator

```
calculateEvaluationScore(scores) = (artistry + commerciality + buzz + targetFit) / 4
    → 소수 첫째 자리까지 반올림 (예: 3.75 → 3.8)

calculateOverallScore(allScores):
    allScores.length === 0  →  null            ← 미평가. 0점이 아니다 (US-010)
    그 외                    →  { score: 개별 점수들의 평균(소수 첫째 자리 반올림), count: 개수 }
```

> **평균의 평균이 아니라 개별 평가 점수의 평균**이다. 평가마다 항목 수가 같으므로(4개 고정) 두 방식의 결과가 동일하지만, 정의를 명확히 해 둔다.

### 6.3 X2 — SerializationGate 알고리즘

**출처**: FR-022, BR-U1-011, BR-U1-012

```
serialize(ctx, entityName, data):
    1. data가 배열이면 각 원소에 대해 재귀 호출 후 배열 반환
    2. data가 객체가 아니면 그대로 반환 (원시값)
    3. 결과 = {}
    4. data의 각 (key, value)에 대해:
         a. RELATION_MAP[entityName][key] 가 존재하면  ← 중첩 엔티티
              canReadEntity(role, 자식엔티티) 가 false면  → 건너뜀 (키 자체를 넣지 않음)
              아니면 결과[key] = serialize(ctx, 자식엔티티, value)   ← 재귀
         b. 아니면 (일반 필드)
              canReadField(role, entityName, key) 가 false면  → 건너뜀
              아니면 결과[key] = convert(value)
    5. 결과 반환

convert(value):
    bigint  →  십진 문자열          ← domain-entities.md 1.1절
    Date    →  ISO 8601 문자열
    그 외    →  그대로
```

**핵심 규칙 3가지**

| # | 규칙 | 이유 |
|---|---|---|
| 1 | 차단된 키는 **결과 객체에 넣지 않는다.** `null` 대입이 아니다 | US-014의 수용 기준이 "키 자체가 없다"고 명시 |
| 2 | `RELATION_MAP`에 없는 중첩 객체는 **차단**한다 | 새 관계를 추가하고 등록을 잊으면 하위 객체 전체가 미검증 상태로 노출된다. 기본값을 차단으로 두어 실패가 안전한 방향으로 일어나게 한다 (BR-U1-012) |
| 3 | `FinancialModel`처럼 **엔티티 단위 차단**이 있으면 관계 필드째로 제거한다 | 필드를 하나씩 지우면 빈 객체 `{}`가 남아 "재무 데이터가 있긴 하다"는 정보가 새어 나간다 |

**RELATION_MAP 초기값**

| 부모.필드 | 자식 엔티티 |
|---|---|
| `Title.deal` | `Deal` |
| `Title.financialModel` | `FinancialModel` |
| `Title.rightsGrants` | `RightsGrant` |
| `Title.evaluations` | `Evaluation` |
| `Title.comments` | `Comment` |
| `Title.festivalRecords` | `FestivalRecord` |
| `Title.stageTransitions` | `StageTransition` |
| `Title.assignee` | `User` |
| `Evaluation.evaluator` | `User` |
| `Comment.author` | `User` |
| `StageTransition.changedBy` | `User` |
| `Notification.title` | `Title` |

**내보내기용 변형**

```
serializeForExport(ctx, entityName, rows, columns):
    1. rows를 serialize로 처리한다
    2. columns에서 차단된 필드에 해당하는 항목을 제거한다   ← 빈 열이 남지 않게
    3. { rows: 처리된 행, columns: 남은 컬럼 } 반환
```

> **호출 순서가 중요하다**: `serializeForExport` → `D4.serializeToCsv`. 역순이면 마스킹 대상 값이 이미 문자열에 포함된 뒤 제거를 시도하게 된다 (services.md 5.3절).

## 7. 인증·계정 관리 흐름

### 7.1 로그인

```
POST /api/auth/login
 1. 입력 검증 (email 형식, password 존재)              실패 → 400
 2. email 소문자 정규화
 3. 사용자 조회
 4. 사용자 없음 → 더미 해시에 대해 검증 연산 수행 후 401   ← BR-U1-002 타이밍 차단
 5. 비밀번호 해시 검증                                  불일치 → 401
 6. Session 생성 (expiresAt = now + 12h)
 7. 세션 쿠키 설정 (httpOnly, sameSite=lax, Max-Age 없음)
 8. 사용자 정보 반환 (X2 통과 → passwordHash 제거됨)
```

### 7.2 요청별 컨텍스트 확립 (X5)

```
모든 인증 필요 요청
 1. 쿠키에서 세션 ID 추출              없음 → 401
 2. Session 조회                       없음 → 401
 3. expiresAt <= now 확인              만료 → 세션 삭제 후 401
 4. User 조회                          없음 → 세션 삭제 후 401  ← 계정이 삭제된 경우
 5. ctx = { userId, role: user.role, now: 요청 시각 }
```

> **`now`를 컨텍스트에 담는 이유**: 순수 도메인 모듈이 현재 시각을 스스로 읽지 않고 인자로 받게 하기 위함이다(components.md 4절). 한 요청 안의 모든 계산이 동일한 시각을 쓰므로 결과가 일관된다.

### 7.3 계정 생성

```
POST /api/users   (Executive 전용)
 1. requireRole(ctx, EXECUTIVE)                        불일치 → 403
 2. 입력 검증 (email·name·password·role)                실패 → 400
 3. email 중복 확인                                     중복 → 409 CONFLICT
 4. password를 argon2id로 해시
 5. User 생성
 6. 생성된 사용자 반환 (passwordHash 제거됨)
```

### 7.4 역할 변경 / 계정 삭제 (트랜잭션 T6)

```
PATCH /api/users/:id/role   |   DELETE /api/users/:id
 1. requireRole(ctx, EXECUTIVE)                        불일치 → 403
 2. 대상 사용자 조회                                     없음 → 404
 3. 트랜잭션 시작
      a. 대상 행을 잠근다 (SELECT ... FOR UPDATE)
      b. 대상이 EXECUTIVE인가?
           예 → EXECUTIVE 총 수 조회
                총 수 === 1  →  409 LAST_EXECUTIVE (롤백)
      c. 역할 변경 또는 삭제 수행
      d. 삭제인 경우 해당 사용자의 Session 전부 삭제 (cascade)
    트랜잭션 종료
 4. 결과 반환
```

**행 잠금이 필요한 이유**: BR-U1-009의 경쟁 상태 — 두 Executive가 동시에 서로를 강등하면 두 트랜잭션 모두 "2명이니 괜찮다"고 판단해 Executive가 0명이 될 수 있다.
