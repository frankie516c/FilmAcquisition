# Business Rules — U1 Foundation & Auth

**작성일**: 2026-07-25
**단계**: 🟢 CONSTRUCTION — U1 Functional Design

각 규칙에 출처 스토리·요구사항 ID를 표기한다. 규칙 ID는 `BR-U1-nnn` 형식이다.

---

## 1. 인증 규칙

### BR-U1-001 — 로그인 판정
**출처**: US-026, FR-021

이메일과 비밀번호로 인증한다. 판정 순서는 다음과 같다.

1. 이메일을 소문자로 정규화한다
2. 해당 이메일의 사용자를 조회한다
3. 사용자가 없으면 → **실패**
4. 비밀번호 해시를 검증한다. 불일치하면 → **실패**
5. 성공 시 세션을 생성하고 쿠키를 설정한다

### BR-U1-002 — 로그인 실패 응답의 정보 노출 차단
**출처**: US-026 (*"두 경우 모두 동일한 실패 메시지"*), NFR-005

- 계정 없음과 비밀번호 불일치를 **구분하지 않고** 동일한 응답을 반환한다
  - 코드: `AUTHENTICATION_FAILED` · 상태: 401 · 메시지: `이메일 또는 비밀번호가 올바르지 않습니다.`
- **타이밍 차이도 차단한다**: 사용자가 존재하지 않아도 더미 해시에 대해 검증 연산을 수행한 뒤 실패를 반환한다
  > 이유: 계정이 없으면 해시 검증을 건너뛰어 응답이 빨라지고, 응답 시간 차이로 계정 존재 여부가 드러난다. argon2 검증은 의도적으로 느리므로 이 차이가 측정 가능한 수준이다.

### BR-U1-003 — 비밀번호 저장
**출처**: US-026 (*"평문이 아닌 해시값만 저장"*), NFR-005

- 알고리즘: **argon2id**
- `passwordHash`는 **어떤 역할에게도 응답에 포함되지 않는다** — 필드 정책에서 전 역할 차단 (3.2절)
- 로그·오류 메시지에 비밀번호 원문이나 해시가 남지 않는다

### BR-U1-004 — 세션 수명
**출처**: US-026 (*"브라우저를 완전히 종료하면 세션 만료"*), Q1=A

| 층위 | 규칙 |
|---|---|
| 쿠키 | `httpOnly`, `sameSite=lax`, `path=/`. **`Max-Age`·`Expires` 미지정** → 브라우저 종료 시 소멸 |
| 서버 | `Session.expiresAt` = 생성 시각 + 12시간 |
| 검증 | 매 요청마다 세션 존재 + `expiresAt > now` 확인. 만료 시 세션 삭제 후 401 |

### BR-U1-005 — 역할의 즉시 반영
**출처**: US-028 (*"변경이 즉시 반영되어 다음 요청부터 새 역할의 권한이 적용된다"*), Q1=A

- 세션 쿠키에는 **세션 ID만** 담고 역할을 담지 않는다
- 매 요청마다 `Session → User`를 조회해 **현재 역할**을 읽는다
- 따라서 Executive가 역할을 바꾸면 대상 사용자의 다음 요청부터 새 권한이 적용된다 (재로그인 불필요)

### BR-U1-006 — 로그아웃
**출처**: US-026

로그아웃 시 서버의 세션 레코드를 **삭제**하고 쿠키를 만료시킨다. 쿠키만 지우고 서버 세션을 남기지 않는다.

## 2. 계정 관리 규칙

### BR-U1-007 — 계정 생성 권한과 초기 비밀번호
**출처**: US-028, FR-023, Q2=A

- **Executive만** 계정을 생성할 수 있다
- Executive가 이메일·이름·**초기 비밀번호**·역할을 직접 지정한다
- 최초 로그인 시 비밀번호 변경을 강제하지 않는다
  > 근거: 비밀번호 변경 화면·API·상태 플래그는 US-026~029 어느 수용 기준도 요구하지 않는다. PoC 범위를 넘는 기능을 추가하지 않는다.

### BR-U1-008 — 이메일 중복 차단
**출처**: US-028

이미 존재하는 이메일로 계정 생성 시 → `CONFLICT` · 409 · `이미 사용 중인 이메일입니다.`

### BR-U1-009 — 마지막 Executive 보호
**출처**: US-029, FR-023, 트랜잭션 T6

**규칙**: 시스템에 Executive가 **정확히 1명**일 때, 그 사용자의 역할 변경과 삭제를 거부한다.

| 상황 | 결과 |
|---|---|
| Executive 1명, 그 계정의 역할을 Scout/Analyst로 변경 시도 | **거부** — `LAST_EXECUTIVE` · 409 · `최소 1명의 경영진 계정이 필요합니다.` |
| Executive 1명, 그 계정 삭제 시도 | **거부** — 동일 |
| Executive 2명 이상, 그중 1명의 역할 변경·삭제 | 정상 처리 |
| Executive 1명, **다른 역할** 사용자를 Executive로 승격 | 정상 처리 (보호 대상이 아님) |

**경쟁 상태 방지 (T6)**: "Executive 수 조회 → 변경" 을 **하나의 트랜잭션**으로 묶고, 조회 시 대상 행을 잠근다.
> 이유: 두 Executive가 동시에 서로를 강등하면, 각 트랜잭션이 "2명이니 괜찮다"고 판단해 둘 다 성공하고 Executive가 0명이 된다.

### BR-U1-010 — 자기 자신에 대한 조작
**출처**: US-028, US-029에서 명시되지 않은 경계 상황

| 상황 | 결정 | 근거 |
|---|---|---|
| Executive가 자기 역할을 강등 | BR-U1-009를 적용 (다른 Executive가 있으면 허용) | 별도 규칙을 두지 않는다. 마지막 관리자 보호가 이미 시스템 잠김을 막는다 |
| Executive가 자기 계정을 삭제 | 동일 | 위와 같음 |
| 자기 계정 삭제 성공 시 | 세션을 즉시 무효화하고 로그인 화면으로 보낸다 | 삭제된 사용자의 세션이 살아 있으면 안 된다 |

> **설계 판단**: "자기 자신은 조작 불가"라는 추가 규칙을 두지 않았다. US-029가 요구하는 것은 시스템이 잠기지 않는 것뿐이며, 그 목적은 마지막 관리자 보호만으로 달성된다. 규칙이 적을수록 예외 상황이 줄어든다.

## 3. 권한 규칙

### 3.1 동작 권한 (Action-level) — 12항목
**출처**: requirements.md 3.2절, US-027

권한 없는 호출은 **403 `FORBIDDEN`** 을 반환하고 데이터를 변경하지 않는다.

| # | 리소스·동작 | SCOUT | ANALYST | EXECUTIVE |
|---|---|---|---|---|
| 1 | `title:create/update/delete` | ✅ | ❌ | ❌ |
| 2 | `festivalRecord:create/update/delete` | ✅ | ❌ | ❌ |
| 3 | `evaluation:create/update` | ✅ | ❌ | ❌ |
| 4 | `comment:create` | ✅ | ✅ | ✅ |
| 5 | `pipeline:changeStage` | ✅ | ✅ | ❌ |
| 6 | `deal:update` | ❌ | ✅ | ❌ |
| 7 | `rights:create/update` | ❌ | ✅ | ❌ |
| 8 | `financial:update` | ❌ | ✅ | ❌ |
| 9 | `import:commit` | ✅ | ✅ | ❌ |
| 10 | `export:execute` | ✅ | ✅ | ❌ |
| 11 | `report:generate` | ❌ | ✅ | ✅ |
| 12 | `user:manage` | ❌ | ❌ | ✅ |

**조회 동작**: 위 표에 없는 조회(`read`)는 전 역할에게 허용된다. 조회 차단은 **필드 정책**이 담당한다.

**코멘트 수정·삭제**: 동작 권한이 아니라 **소유권**으로 판정한다. 본인 것만 가능하며 타인 것은 403. (US-011)

### 3.2 필드 권한 (Field-level) — 전 엔티티 전 필드
**출처**: FR-022, US-014, US-027

**핵심 규칙**: **정책 표에 없는 필드는 차단이 기본값이다.**

| 엔티티 | 필드 | SCOUT | ANALYST | EXECUTIVE |
|---|---|---|---|---|
| **User** | `passwordHash` | ❌ | ❌ | ❌ |
| **User** | 그 외 전 필드 | ✅ | ✅ | ✅ |
| **Session** | 전 필드 | ❌ | ❌ | ❌ |
| **Deal** | `offerAmount`, `offerExpiryDate`, `offerSubmittedAt`, `titleId`, `id`, `createdAt`, `updatedAt` | ✅ | ✅ | ✅ |
| **Deal** | `askingPrice`, `minimumGuarantee`, `runningRoyaltyRate`, `contractTerms` | ❌ | ✅ | ✅ |
| **FinancialModel** | 전 필드 (계산 결과 포함) | ❌ | ✅ | ✅ |
| **Title** | 전 필드 | ✅ | ✅ | ✅ |
| **FestivalRecord** | 전 필드 | ✅ | ✅ | ✅ |
| **Evaluation** | 전 필드 | ✅ | ✅ | ✅ |
| **Comment** | 전 필드 | ✅ | ✅ | ✅ |
| **StageTransition** | 전 필드 | ✅ | ✅ | ✅ |
| **RightsGrant** | 전 필드 | ✅ | ✅ | ✅ |
| **Notification** | 전 필드 | ✅ | ✅ | ✅ |

**`Session` 전 필드가 전 역할에게 차단된 이유**: 세션 ID가 응답에 실리면 탈취 위험이 생긴다. 세션은 쿠키로만 전달된다.

### BR-U1-011 — 마스킹의 구현 방식
**출처**: FR-022, US-014, US-027

- 차단된 필드는 **응답 객체에서 키 자체를 제거**한다. `null`이나 빈 문자열로 대체하지 않는다
- 화면 숨김(CSS·조건부 렌더링)만으로 구현하지 않는다
- **CSV·Excel·PDF 내보내기에도 동일 적용**하며, 제거된 필드는 컬럼 목록에서도 빠진다
- 클라이언트에서 숨겨진 UI를 강제로 노출시켜 조작해도 서버가 요청을 거부한다

### BR-U1-012 — 필드 정책 미등재 시 동작
**출처**: 설계 판단 (components.md X1)

정책 표에 등재되지 않은 필드는 **모든 역할에게 차단**된다.

> **이유**: 새 필드를 추가하고 정책 등록을 잊었을 때, 기본값이 "허용"이면 민감 정보가 조용히 노출된다. 기본값이 "차단"이면 "보여야 할 게 안 보인다"는 눈에 띄는 버그로 나타난다. 실패가 안전한 방향으로 일어나게 한다.

## 4. 검증 규칙

### BR-U1-013 — 공통 문자열 규칙

| 규칙 | 내용 |
|---|---|
| 앞뒤 공백 | 저장 전 `trim` |
| 빈 문자열 | 필수 필드에서 `trim` 후 빈 문자열이면 미입력으로 간주 → 검증 실패 |
| 선택 필드의 빈 문자열 | `null`로 정규화해 저장 |

### BR-U1-014 — 필드별 검증 규칙

| 대상 | 규칙 | 위반 시 코드 |
|---|---|---|
| `email` | RFC 형식 + 최대 254자 + 소문자 정규화 | `INVALID_EMAIL` |
| `password` | 8자 이상 (상한 없음) | `PASSWORD_TOO_SHORT` |
| `name` | 1~50자 | `INVALID_LENGTH` |
| `role` | Role 열거형 값 | `INVALID_ENUM` |
| 금액 필드 전체 | **비음수 정수**. 소수·음수·문자 거부 | `INVALID_AMOUNT` |
| 금액 상한 | 8바이트 정수 범위 (약 922경) | `AMOUNT_OUT_OF_RANGE` |
| 평가 점수 4종 | 1~5 **정수**. 0·6·소수 거부 | `SCORE_OUT_OF_RANGE` |
| `runningRoyaltyRate` | 0~100 (소수 허용) | `RATE_OUT_OF_RANGE` |
| `productionYear`, 영화제 `year` | 1888 ~ (현재연도+10) | `YEAR_OUT_OF_RANGE` |
| `runtimeMinutes` | 1~600 정수 | `RUNTIME_OUT_OF_RANGE` |
| `genres` | 최소 1개, Genre 열거형 | `REQUIRED` / `INVALID_ENUM` |
| `territories` | 최소 1개, Territory 열거형 | `REQUIRED` / `INVALID_ENUM` |

### BR-U1-015 — 날짜 순서 규칙

| 대상 | 규칙 | 코드 | 출처 |
|---|---|---|---|
| `Deal.offerExpiryDate` | **≥** `offerSubmittedAt` (같은 날 허용) | `INVALID_DATE_ORDER` | US-013 |
| `RightsGrant.contractEndDate` | **>** `contractStartDate` (같은 날 **거부**) | `INVALID_DATE_ORDER` | US-015 |

> **두 규칙의 부등호가 다르다.** 오퍼는 당일 제출·당일 만료가 실무상 가능하지만, 계약 기간이 0일인 판권은 의미가 없다. US-015의 수용 기준이 *"종료일을 시작일과 같거나 이전 날짜로 입력하면 거부"* 라고 명시한다.

### BR-U1-016 — 검증 실패 응답
**출처**: US-001·US-009·US-013의 폼 오류 표시 요구, Q5=A

- 여러 필드가 동시에 실패하면 **전부 수집해 한 번에 반환**한다. 첫 실패에서 중단하지 않는다
- 응답의 `fields` 배열에 필드 경로·코드·메시지를 담는다 (5.2절)

## 5. 오류 처리 규칙

### 5.1 오류 타입과 HTTP 매핑
**출처**: X3 ErrorMapper

| 도메인 오류 | HTTP | 대표 코드 |
|---|---|---|
| `ValidationError` | **400** | `VALIDATION_FAILED` |
| `AuthenticationError` | **401** | `AUTHENTICATION_FAILED` |
| `ForbiddenError` | **403** | `FORBIDDEN` |
| `NotFoundError` | **404** | `NOT_FOUND` |
| `ConflictError` | **409** | `CONFLICT`, `LAST_EXECUTIVE` |
| 그 외 예외 | **500** | `INTERNAL_ERROR` |

### 5.2 응답 본문 형식
**출처**: Q5=A

```jsonc
{
  "error": {
    "code": "VALIDATION_FAILED",
    "message": "입력값을 확인해주세요.",
    "fields": [
      { "path": "titleKo",        "code": "REQUIRED",           "message": "제목을 입력해주세요." },
      { "path": "productionYear", "code": "YEAR_OUT_OF_RANGE",  "message": "제작연도는 1888년 이후여야 합니다." }
    ]
  }
}
```

- `code` — 기계 판독용. 클라이언트 분기에 사용
- `message` — 한국어 사용자 메시지
- `fields` — **검증 실패 시에만 존재**. 다른 오류에는 없다

### BR-U1-017 — 500 오류의 정보 노출 차단
**출처**: NFR-005

예상하지 못한 예외는 스택 트레이스·내부 메시지·SQL을 응답에 담지 않는다. 서버 로그에만 기록하고 클라이언트에는 `INTERNAL_ERROR` · `요청을 처리하지 못했습니다.` 만 반환한다.

### BR-U1-018 — 404와 403의 구분
**출처**: 설계 판단

| 상황 | 응답 |
|---|---|
| 리소스가 없음 | 404 |
| 리소스는 있으나 동작 권한 없음 | 403 |

> 존재 여부를 숨기기 위해 403 대신 404를 반환하는 방식은 쓰지 않는다. 본 시스템은 로그인한 내부 사용자만 접근하며, 전 역할이 작품 목록을 볼 수 있으므로 존재 자체가 비밀이 아니다. 오히려 403이 "권한이 없다"는 정확한 안내가 된다.

## 6. 표기 규칙
**출처**: US-032, NFR-004

### BR-U1-019 — 금액 표기
- 통화는 **KRW 단일**. 통화 선택·전환 수단을 제공하지 않는다
- 표시: 천 단위 구분 기호 + `원` (예: `1,250,000,000원`)
- API 응답에서는 **문자열**로 전달 (BigInt 직렬화, domain-entities.md 1.1절)
- 클라이언트는 표시만 담당하고 금액 산술을 하지 않는다

### BR-U1-020 — 날짜·시간대 표기
- 표시 형식: `YYYY-MM-DD`
- 시간대: **Asia/Seoul 고정.** 사용자 브라우저 시간대를 따르지 않는다
- 날짜 계산(D-day, 체류 일수)은 Asia/Seoul 달력일 경계 기준 (business-logic-model.md 4절)
- DB 저장은 UTC, 표시·계산 시 Asia/Seoul로 변환

### BR-U1-021 — 언어
- UI 텍스트는 **한국어 단일**. 언어 전환 수단을 제공하지 않는다
- 열거형 표시명은 코드 상수의 매핑을 사용한다 (domain-entities.md 2절)

## 7. 실행 환경 규칙

### BR-U1-022 — 기동 절차
**출처**: US-030

`docker compose up` 시 다음 순서로 진행한다.

1. PostgreSQL 컨테이너 기동 및 **healthcheck 통과 대기**
2. 앱 컨테이너에서 필수 환경변수 존재 확인 → 누락 시 **기동 실패** (명확한 메시지와 함께)
3. Prisma 마이그레이션 적용
4. 시드 멱등 적재 (BR-U1-023)
5. Next.js 서버 시작

### BR-U1-023 — 시드 멱등성
**출처**: US-030 (*"재기동 시 기존 데이터가 유지되고 시드가 중복 적재되지 않는다"*)

- 시드는 **`User` 테이블이 비어 있을 때만** 실행한다
- 이미 데이터가 있으면 건너뛰고 `시드 데이터가 이미 존재합니다. 건너뜁니다.` 를 로그에 남긴다
- 판정 기준을 `User` 테이블로 삼는 이유: 사용자 없이 시스템이 동작할 수 없으므로 가장 신뢰할 수 있는 지표다

### BR-U1-024 — 비밀 정보 관리
**출처**: US-030, NFR-005

| 항목 | 규칙 |
|---|---|
| DB 접속 정보, 세션 비밀키 | 환경변수로 주입. **소스코드 하드코딩 금지** |
| `.env` | 버전 관리에서 제외 |
| `.env.example` | 키 이름과 형식만 포함, 실제 값 없음 |
| 필수 환경변수 | `DATABASE_URL`, `SESSION_SECRET` |

### BR-U1-025 — 시드 계정의 성격
**출처**: US-031, NFR-005

- 데모 계정 3개의 비밀번호는 `.env.example`과 README에 공개된 값을 쓴다
- **이는 로컬 PoC 전제이며 실제 운영에 사용할 수 없다.** 이 사실을 README에 명시한다
> requirements.md 2.3절이 이미 "실제 인수 업무에 사용하려면 보안 확장 활성화 후 재설계가 필요하다"고 기록했다. 시드 계정도 그 범위에 포함된다.
